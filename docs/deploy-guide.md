# Руководство по развёртыванию MailSense

Документ для администратора: как развернуть серверную часть, где лежат данные, как обновлять,
как делать резервные копии и что делать, если что-то не поднялось. Рассчитан на человека, который
умеет работать с Docker и внутренней сетью, но не обязан знать устройство приложения.

Короткая версия для опытных — раздел «Быстрый старт». Остальное — пояснения и процедуры.

---

## 1. Что именно разворачивается

Целевая топология 0.1.4 (решения Р15–Р17):

    рабочие места сотрудников                    сервер предприятия
    ┌───────────────────────────┐               ┌──────────────────────────────┐
    │ MailSense (Electron)      │  HTTPS/HTTP   │ mailsense — сервер СЭД       │
    │ • локальный backend :8123 │ ────────────► │ • служебные ящики аппарата   │
    │ • почта берётся с сервера │               │ • журнал, резолюции, аудит   │
    │ • личные черновики/подпись│               │ • пользователи, права, AD    │
    └───────────────────────────┘               │ • PostgreSQL (внутри)        │
                                                └──────────────────────────────┘

- **Сервер** держит служебные ящики аппарата (внутренний делопроизводственный и внешнюю приёмную),
  документооборот, пользователей и аудит. Это два контейнера: приложение и PostgreSQL.
- **Клиенты** — приложения Electron на машинах сотрудников. Почта им не хранится: они получают её
  с сервера. Личные настройки (подпись, шаблоны, черновики) остаются на рабочем месте.
- **Браузерный доступ** к серверу остаётся и используется для администрирования и диагностики,
  но рабочим местом для сотрудников он не является: вся переписка аппарата легла бы на сервер.

---

## 2. Требования

| Что | Требование |
|---|---|
| Docker | Docker Engine 24+ и Compose v2 (`docker compose`) |
| Ресурсы | 2 ядра, 4 ГБ ОЗУ, диск — по объёму почты и вложений (плюс запас на резервные копии) |
| Сеть | Сервер в внутренней сети; рабочие места видят его по имени или IP |
| Каталог | Доступ к контроллеру домена по LDAP/LDAPS (порт 389 или 636) |
| Почта | Доступ к почтовому серверу: IMAP или POP3 для приёма, SMTP для отправки |
| ИИ | Внутренние эндпоинты моделей (OpenAI-совместимые), интернет не требуется |
| Порты | Наружу публикуется только 8123 (при необходимости закрывается reverse proxy с TLS) |

Учётные данные AD, ящиков и моделей в репозитории не хранятся: они вводятся в интерфейсе или
в `.env` на сервере.

---

## 3. Быстрый старт

```bash
# 1. Получить файлы на сервер (каталог mailsense/docker)
git clone <адрес репозитория> && cd mailsense/docker

# 2. Заполнить настройки
cp .env.example .env
nano .env            # POSTGRES_PASSWORD обязательно; TZ; при необходимости пути данных

# 3. Собрать и запустить
docker compose -f docker-compose.yml up -d --build

# 4. Проверить, что поднялось (оба сервиса healthy)
docker compose -f docker-compose.yml ps
curl -s http://127.0.0.1:8123/api/health

# 5. Войти администратором
#    Открыть http://<сервер>:8123 в браузере и войти логином из MAILSENSE_ADMIN_LOGINS
```

Если в `MAILSENSE_ADMIN_LOGINS` не указать ни одного логина, **администратора не будет ни у кого** —
это самая частая причина «вошёл, а настроек нет».

## 3a. Что задаётся в `.env`, а что в интерфейсе

Важно не искать в `.env` того, чего там нет: каталог и почта настраиваются **в приложении**,
потому что это предметные настройки предприятия, а не параметры контейнера.

| Что | Где задаётся | Почему так |
|---|---|---|
| Пароль базы, вход администратора | `.env` (`POSTGRES_*`, `MAILSENSE_ADMIN_*`) | нужно до первого запуска |
| Адреса и модели ИИ (выжимка и OCR отдельно) | `.env` (`MAILSENSE_AI_*`) | инфраструктура, одинаковая для всех |
| Часовой пояс | `.env` (`TZ`) | определяет «сегодня» для сроков и журнала |
| Пути данных | `.env` (`MAILSENSE_DATA_PATH`, `POSTGRES_DATA_PATH`) | удобство администрирования и бэкапа |
| **Каталог (AD)**: адрес, служебная учётная запись, база поиска | `.env` (`MAILSENSE_LDAP_*`) **или** интерфейс: Настройки → Каталог (LDAP) | пароль bind хранится в базе зашифрованным; правка в интерфейсе важнее переменной |
| **Почтовые ящики** (IMAP/POP3 + SMTP, логины, пароли) | `.env` (`MAILSENSE_MAILBOXES`) **или** интерфейс: Настройки → Почта | пароли шифруются ключом из `data/`; ящиков может быть много |
| **Служебные ящики**: какой внутренний (делопроизводство), какой внешняя приёмная | `.env` (`MAILSENSE_SERVICE_MAILBOX`, `MAILSENSE_EXTERNAL_MAILBOX`) **или** интерфейс: Настройки → Служебные ящики | это роли конкретных ящиков, а не адреса серверов |
| Типовые сроки, правила сортировки | **интерфейс** | настройки процесса, меняются администратором |

### Развёртывание целиком из окружения

Чтобы не заходить в интерфейс вовсе, задайте в `.env`:

```ini
# Каталог (AD).
# _LOGIN и _PASSWORD — СЛУЖЕБНАЯ (bind) учётная запись, от имени которой приложение читает каталог:
# ищет сотрудников для выбора исполнителей и наполняет адресную книгу. Это не учётные записи
# работников — каждый входит своей доменной учёткой, и она нигде не сохраняется. Без этой учётки
# адресная книга пуста (поиск идёт только по кэшу), и выбирать исполнителей не из чего.
MAILSENSE_LDAP_URL=ldaps://srv-dc01.enterprise.local:636
MAILSENSE_LDAP_BASE_DN=DC=enterprise,DC=local
MAILSENSE_LDAP_LOGIN=ldap-bind@enterprise.local
MAILSENSE_LDAP_PASSWORD=…

# Ящики — JSON-массивом; protocol: imap|pop3, tls: true/false или none|ssl|starttls (не задано = ssl)
MAILSENSE_MAILBOXES=[{"username":"post@mail.test","password":"…","protocol":"imap","host":"mail.test","port":993,"tls":true,"smtpHost":"mail.test","smtpPort":465,"smtpTls":true}]

# Роли служебных ящиков — адресами, ищутся среди засеянных
MAILSENSE_SERVICE_MAILBOX=post@mail.test
MAILSENSE_EXTERNAL_MAILBOX=info@mail.test
```

Правила, одинаковые для всех настроек засева:

1. **Значение из окружения применяется только там, где настройки ещё нет в базе.** Заданное
   администратором в интерфейсе всегда важнее и перезапуском контейнера не отменяется.
2. **Повторный запуск безопасен:** ящики создаются только отсутствующие, существующие не
   перезаписываются (пароль мог быть изменён вручную).
3. **Пароли шифруются** тем же механизмом, что интерфейс (ключ из `data/`); в журнал не попадают.
4. **Ошибки засева не мешают старту** — в журнале одна сводка: «Засев из окружения — каталог:
   записано N, пропущено M; ящики: внутренний настроен, внешний НЕ НАЙДЕН».
5. Битый JSON, неполный набор полей, неизвестный протокол или ненайденный адрес ящика —
   пропуск этого элемента с понятной причиной, остальное настраивается.

Исключение — блок `MAILSENSE_SEED_ACCOUNT` в `.env.example`: это **засев одного ящика для стенда**,
чтобы не заводить его руками при разработке. В боевом развёртывании оставьте `false` и пользуйтесь
`MAILSENSE_MAILBOXES`.

## 4. Где лежат данные (папки на хосте, не тома Docker)

Данные вынесены наружу обычными каталогами: администратору нужно видеть размер, складывать рядом
бэкапы и уметь просто скопировать папку.

| Путь на хосте | Что внутри | Можно ли потерять |
|---|---|---|
| `docker/data/` | `mailsense.sqlite` (почтовая база, очереди, пользовательские профили), `attachments/` (вложения писем), ключ шифрования паролей ящиков, `logs/` (журнал приложения) | **Нельзя**: без ключа шифрования пароли ящиков не восстановить |
| `docker/pgdata/` | База документооборота PostgreSQL: журнал, документы, резолюции, пользователи, роли, аудит | **Нельзя** |
| `docker/.env` | Пароль базы и настройки развёртывания | **Нельзя**, но восстанавливается из документации |

Пути меняются в `.env` (`MAILSENSE_DATA_PATH`, `POSTGRES_DATA_PATH`), отсчёт — от каталога `docker/`.
Если хочется отдельный диск под данные, укажите абсолютные пути, например
`MAILSENSE_DATA_PATH=/srv/mailsense/data`.

Проверить логи приложения: `docker/data/logs/mailsense.log` (внутри контейнера — `/data/logs`).
Логи самого контейнера ограничены (10 МБ × 5 файлов), чтобы диск не забивался.

## 5. Первичная настройка

**Первый запуск: документооборот включается сам.** В серверном развёртывании (задан
`DOCFLOW_DATABASE_URL`) на свежей базе система включает документооборот автоматически — иначе вход
администратора не работал бы, а API оставался открытым без аутентификации. В журнале появляется
строка «Свежее серверное развёртывание: документооборот включён автоматически».

| Переменная | Поведение |
|---|---|
| не задана | свежая база → документооборот включается сам; явную настройку администратора система не перетирает |
| `MAILSENSE_DOCFLOW_ENABLED=true` | включить явно и записать настройку |
| `MAILSENSE_DOCFLOW_ENABLED=false` | **только подавить автовключение** (сервер без СЭД); в базу ничего не пишется, включённое позже в интерфейсе решение администратора сохраняется |

Проверено живьём на чистой базе: строка в журнале, настройка `docflow.enabled=true` записана,
миграции применились (8), вход администратором — **200 без ручных действий**. Обратный случай
(`=false`): в базе строки нет, вход отклоняется, потому что документооборот выключен.

⚠️ Если образ собран **до** этой доработки, документооборот придётся включить один раз вручную:

```bash
curl -X PUT http://127.0.0.1:8123/api/docflow/settings \
     -H 'Content-Type: application/json' -d '{"enabled":true}'
```

Порядок, в котором настраивают систему на новом сервере:

1. **Документооборот** — включить (см. предупреждение выше).
2. **Каталог (AD).** Настройки → каталог: адрес контроллера домена, база поиска, служебная учётная
   запись для чтения. Проверить кнопкой подключения. Без каталога не будет выбора исполнителей
   и входа доменными учётными записями.
3. **Администраторы.** Убедиться, что логины из `MAILSENSE_ADMIN_LOGINS` вошли и получили роль
   администратора; аварийный локальный администратор — только на случай недоступности AD.
4. **Служебные ящики** (Настройки → «Служебные ящики»):
   - *внутренняя (делопроизводство)* — с неё уходит письмо руководителю и исполнителям;
   - *внешняя (приёмная)* — куда приходит внешняя почта.
   На пилот можно назначить один ящик на обе роли: система предупредит, но не запретит.
   Сканирование ящика выполняет аппарат (право почты), а не администратор.
5. **ИИ-модели** (Настройки → ИИ): адрес и имя модели выжимки, отдельно модель OCR.
   Кнопка проверки связи показывает, отвечает ли эндпоинт. Модели только внутренние.
6. **Роли и права.** Роли: администратор и секретариат (аппарат) — с правами почты
   (`mail.view`, `mail.send`); руководитель, подписант и исполнитель почту не видят:
   исполнитель открывает письмо-источник прямо из своей задачи.
7. **Типовые сроки и правила сортировки** — по желанию заказчика.
8. **Проверка цикла**: внешнее письмо → регистрация в журнале → поручение → утверждение подписантом →
   отправка исполнителям → отчёт исполнителя → закрытие. Это же и есть приёмка развёртывания
   (см. раздел 10).

## 6. Раздача рабочим местам

1. Собрать комплект с адресом сервера внутри (см. `docs/deploy.md`, раздел «Адрес сервера в комплекте»):

   ```bash
   make package-win SERVER_URL=http://mail.enterprise.local:8123
   ```

   Либо положить файл `server.json` рядом с `MailSense.exe` в готовом комплекте:

   ```json
   { "serverUrl": "http://mail.enterprise.local:8123" }
   ```

2. Раздать комплект сотрудникам. При запуске адрес подхватывается автоматически и в настройках
   показан как «Адрес задан администратором — изменить нельзя».
3. Сотрудник входит своей доменной учётной записью. Аппарат работает со служебными ящиками,
   исполнитель видит свои задачи.

Требования к рабочему месту: Windows 10/11 x64, 4 ГБ ОЗУ, доступ к серверу по сети.

## 7. Обновление версии

```bash
cd mailsense/docker
docker compose -f docker-compose.yml down          # остановить (данные остаются в папках)
cp -r data ../backup-data-$(date +%F)              # резервная копия данных (см. раздел 8)
cp -r pgdata ../backup-pgdata-$(date +%F)
cd .. && git pull                                  # получить новую версию
cd docker && docker compose -f docker-compose.yml up -d --build
docker compose -f docker-compose.yml ps            # дождаться healthy
curl -s http://127.0.0.1:8123/api/health
```

Миграции баз применяются автоматически при старте сервера. Откат версии требует восстановления
резервной копии — поэтому копия делается **до** обновления.

## 8. Резервное копирование и восстановление

**Что копировать:** `docker/data`, `docker/pgdata`, `docker/.env`.

**Как часто:** данные документооборота и почты — ежедневно; перед каждым обновлением — обязательно.

### Вариант «остановить и скопировать» (простой и надёжный)

```bash
cd mailsense/docker
docker compose -f docker-compose.yml stop mailsense
cp -a data /backup/mailsense-data-$(date +%F)
cp -a pgdata /backup/mailsense-pgdata-$(date +%F)
docker compose -f docker-compose.yml start mailsense
```

Сервер недоступен только на время копирования (минуты). Почта в это время остаётся на почтовом
сервере и будет забрана при следующем скане — потерь нет.

### Вариант «без остановки» (для больших объёмов)

```bash
# Почтовая часть и вложения
cp -a mailsense/docker/data /backup/mailsense-data-$(date +%F)
# Документооборот — логическим дампом, он согласован по транзакциям
docker exec mailsense-db pg_dump -U mailsense mailsense | gzip > /backup/mailsense-db-$(date +%F).sql.gz
```

Файл SQLite в `data/` копируется в режиме WAL: для гарантированно согласованной копии останавливайте
сервис `mailsense` (первый вариант) либо копируйте вместе с `-wal` и `-shm`.

### Восстановление

```bash
cd mailsense/docker
docker compose -f docker-compose.yml down
rm -rf data pgdata
cp -a /backup/mailsense-data-2026-10-08 data
cp -a /backup/mailsense-pgdata-2026-10-08 pgdata
docker compose -f docker-compose.yml up -d
curl -s http://127.0.0.1:8123/api/health
```

Для варианта с дампом: поднять пустую базу, затем `gunzip -c dump.sql.gz | docker exec -i mailsense-db psql -U mailsense -d mailsense`.

**Проверяйте восстановление** хотя бы раз на тестовом сервере: непроверенная копия копией не является.

## 9. Сеть, безопасность, TLS

- Наружу публикуется только порт **8123**. Порт базы данных не публикуется вообще.
- Для боевой работы рекомендуется **reverse proxy с TLS** (nginx, внутренний сертификат):

  ```nginx
  server {
    listen 443 ssl;
    server_name mail.enterprise.local;
    ssl_certificate     /etc/ssl/certs/mailsense.crt;
    ssl_certificate_key /etc/ssl/private/mailsense.key;
    client_max_body_size 50m;          # вложения писем
    location / {
      proxy_pass http://127.0.0.1:8123;
      proxy_set_header Host $host;
      proxy_set_header X-Real-IP $remote_addr;
      proxy_set_header X-Forwarded-Proto $scheme;
    }
  }
  ```

  После этого в `SERVER_URL` для клиентов указывается `https://mail.enterprise.local`.
- Доступ к серверу ограничивается внутренней сетью (файрвол): наружу сервер выставлять не нужно.
- Секреты (`.env`, ключ шифрования в `data/`) — только для администратора; в резервные копии
  они попадают, поэтому копии тоже защищаются.
- Часовой пояс (`TZ`) — часть настроек предприятия: от него зависит, какой сегодня день.

## 10. Приёмка развёртывания (чеклист)

1. `docker compose ps` — оба сервиса **healthy**, перезапусков нет.
2. `GET /api/health` отвечает 200.
3. Администратор входит, видит настройки; в журнале аудита есть запись о входе.
4. Каталог AD подключён, поиск сотрудника работает.
5. Служебные ящики назначены; скан ящика аппаратом приносит письма.
6. Внешнее письмо регистрируется в журнале, номер выдаёт система.
7. Поручение уходит руководителю, резолюция утверждается подписантом и dispatch проходит.
8. Исполнитель видит задачу и открывает письмо-источник; почту он не видит (403).
9. Аппарат отправляет письмо с личной подписью работника; в «Отправленных» копия есть.
10. Резервная копия сделана и **проверена восстановлением** на тестовом сервере.

## 11. Диагностика

| Симптом | Что проверить |
|---|---|
| Контейнер перезапускается | `docker compose logs mailsense` — чаще всего неверный пароль в `DOCFLOW_DATABASE_URL` или база ещё не готова |
| `/api/health` не отвечает | Порт занят другим процессом; смотреть `docker compose ps` и логи |
| Вошёл, но настроек нет | Логин не указан в `MAILSENSE_ADMIN_LOGINS`; роль выдаётся при первом входе |
| Почта не приходит | Настройки ящика (IMAP/POP3, пароль); скан запускает аппарат; смотреть журнал приложения |
| Пароли ящиков «слетели» | Потерян ключ шифрования (`data/`) — восстанавливать из резервной копии |
| Даты сроков «сдвинуты» | `TZ` в `.env`; после изменения — `docker compose up -d` |
| Место на диске кончается | Растут `data/attachments` и логи; чистить вложения удалённых писем, настроить ротацию копий |
| Клиент не видит сервер | `server.json` рядом с `MailSense.exe`; доступность 8123 с рабочего места |

Полезные команды:

```bash
docker compose -f docker-compose.yml logs -f mailsense     # журнал сервера
docker compose -f docker-compose.yml exec mailsense sh     # внутрь контейнера
docker compose -f docker-compose.yml exec postgres psql -U mailsense -d mailsense
tail -f data/logs/mailsense.log                            # журнал приложения на хосте
```
