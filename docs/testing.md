# Тестирование и стенд

## Правило: полное покрытие и проверка UI через Playwright

**Это условие приёмки, а не пожелание.** Изменение не считается сделанным, пока оно не покрыто
тестами, а правка интерфейса — ещё и не проверена в браузере.

1. **Новая логика — новые тесты.** Покрываем поведение, а не реализацию: краевые случаи, пустые
   значения, отказы, границы. Тест, который пройдёт при сломанном коде, бесполезен.
2. **Найденный баг — сначала тест, потом починка.** Иначе он вернётся. Так уже нашлись:
   текст до первого `From ` в mbox; обрыв POP3-соединения в `quit()`; письма не доходили
   до получателя (см. `mail.md`); подписант терялся на пути «ответом письмом».
3. **Правка интерфейса — обязательный прогон Playwright.** Открыть затронутый экран, проверить
   **обе роли** (администратор и рядовой сотрудник), убедиться, что **консоль пуста**.
4. **Покрытие не должно падать.** Перед завершением работы — замер и сравнение с рубежом.

(см. `analysisService.test.ts`), `pdfjs-dist/legacy/build/pdf.mjs` (см. `attachments/pdf.test.ts`,
ошибка «Cannot use 'import.meta' outside a module»). Подменяем именно **границу с библиотекой**,
а свою логику проверяем по-настоящему.

## Как проверять

```bash
# Юнит-тесты (--runInBand обязателен: иначе jest поднимает воркеры дочерними процессами)
cd packages/core    && node node_modules/jest/bin/jest.js --runInBand --forceExit
cd packages/docflow && node node_modules/jest/bin/jest.js --runInBand --forceExit
cd packages/server  && node node_modules/jest/bin/jest.js --runInBand --forceExit
cd packages/web     && node node_modules/jest/bin/jest.js --runInBand --forceExit

# Покрытие (в любом пакете)
cd packages/docflow && node node_modules/jest/bin/jest.js --runInBand --forceExit \
  --coverage --coverageReporters=text-summary \
  --collectCoverageFrom="src/**/*.ts" --coveragePathIgnorePatterns="test.ts"

# Сквозные сценарии (нужен запущенный стенд)
node scripts/test_docflow_auth.mjs          # вход и роли
node scripts/test_journal.mjs               # журнал: 35 проверок
node scripts/test_resolutions.mjs           # API резолюций: 29 проверок
node scripts/test_roles_e2e.mjs             # по РОЛЯМ: 93 проверки, четыре роли + админ
node scripts/test_stage5_notifications.mjs  # этап 5: уведомления и сроки — 177 проверок
node scripts/test_stage5_sorting.mjs        # этап 5: правила сортировки — 78 проверок
node scripts/test_pipeline_director.mjs     # пайплайн заказчика НАСТОЯЩИМИ письмами — 62 проверки
node scripts/test_ai_fields.mjs             # стык ИИ и СЭД: письмо с PDF → анализ → форма, черновики — 73 проверки
```

⚠️ `test_ai_fields.mjs` — живой сценарий стыка ИИ с СЭД (письмо с PDF из каталога
`test mail/тестовые письма`): «Скан» → анализ ИИ → автозаполнение формы регистрации в журнале →
ответ руководителя письмом → черновик РЕЗОЛЮЦИИ кнопкой «Заполнить с помощью ИИ» → отправка →
ответ исполнителя письмом → черновик ОТЧЁТА → подтверждение аппаратом. Проверяет поля формы
(номер отправителя, дата, листы, отправитель, краткое содержание), что номер выдаёт база,
что без нажатия кнопки поле пустое и что поручение само не закрывается. Ему нужны переменные
`STAND_MAIL_DIRECTOR_PASS`, `STAND_MAIL_EXECUTOR_PASS` (для ответов письмами), `STAND_ADMIN_PASS`
(настройки ИИ) и опционально `PDF_DIR`. Негативные проверки временно переключают
`ai.baseUrl` на нерабочий порт и **возвращают настройки в конце**.
Кейс «промежуточный ответ исполнителя» до пересборки T23 помечен как ожидание, а не провал.

⚠️ `test_pipeline_director.mjs` шлёт **реальные письма** через SMTP стенда и сканирует ящики по IMAP:
внешнее письмо → служебный ящик аппарата → письмо директору из приложения → ответ директора письмом →
`mark-approval` → `dispatch` → исполнитель → отчёт. Ему нужны переменные
`STAND_MAIL_SERVICE_PASS`, `STAND_MAIL_DIRECTOR_PASS`, `STAND_MAIL_EXECUTOR_PASS`
(и `STAND_MAIL_PARTNER_PASS` для резервного отправителя) плюс пароли ролей СЭД. Письма живут
в реальных ящиках, поэтому проверка «письмо дошло» делается сканом, а не чтением своей же записи.

Сценариям этапа 5 нужны переменные окружения с паролями стенда (`STAND_ADMIN_PASS`,
`STAND_IVANOV_PASS`, `STAND_USER2_PASS`, `STAND_PARTNER_PASS`, `STAND_PETROVA_PASS`) и `BASE_URL`.
Оба печатают «N проверок, 0 провалов» и возвращают 1 при провале — годится для автоматического гейта.

⚠️ **Тесты документооборота требуют PostgreSQL** — они работают с настоящей базой, а не с заглушкой.
Адрес задаётся `DOCFLOW_TEST_DATABASE_URL`
(по умолчанию `postgres://mailsense:testpass@127.0.0.1:55432/mailsense_test`).
Перед прогоном таблицы очищаются (`TRUNCATE`), поэтому база **обязана быть отдельной**: тесты на общей
базе вычищают настройки рабочего экземпляра (проверено на практике).

## Стенд для проверки UI

⚠️ **Стенд локальный, и его пароли — не секрет.** Решение заказчика (2026-10-05): пароли тестовых
учёток опасности не представляют, менять их и переписывать историю git (`git filter-repo`)
**не нужно**. В истории остаётся коммит `0649ca2` с паролями стенда — это осознанно.

Не заводите на это новую работу при следующем обзоре. В скриптах пароли уже вынесены в
переменные окружения (`standPass`) — это просто аккуратность, а не требование безопасности;
возвращать их в код тоже не нужно.

| Что | Значение |
|---|---|
| Приложение | `http://127.0.0.1:8123` |
| Администратор | `test@stand.test` / `Test1234!` |
| Аппарат | `Иванов_ИИ@stand.test` / `IvanovPass123!` |
| Подписант | `user2@stand.test` / `User2Pass123!` |
| Руководитель | `partner@stand.test` / `Partner123!` |
| Исполнитель | `Петрова_МА@stand.test` / `PetrovaPass123!` |
| Каталог | `ldaps://127.0.0.1:636`, bind `ldap-bind@stand.test` / `LdapBind123!` |

**Почтовые ящики** (вход только по полному адресу и почтовому паролю — почтовая и доменная учётки
разные, как на проде): `test@mail.test` / `Test1234!`, `user2@mail.test` / `User2Pass123!`,
`petrova_ma@mail.test` / `PetrovaMail456!`, `ivanov_ii@mail.test` / `IvanovMail456!`.
Полный список — в `test mail/README.md`.

На каждом прогоне проверять: экран входа и шапку (кто вошёл); три панели «папки → список → чтение»;
вкладки настроек для обеих ролей (рядовой **не должен** видеть админских и служебной учётки каталога);
композер; **консоль браузера — ноль ошибок**.

## Сквозной тест по ролям (`scripts/test_roles_e2e.mjs`)

Проверяет **весь путь целиком для каждой роли**, причём отрицательные проверки там не менее важны
положительных: смысл разделения ролей в том, что аппарат НЕ утверждает, подписант НЕ отправляет,
исполнитель НЕ регистрирует.

⚠️ Скрипт идёт в три шага: вход каждой роли (заводит учётки из каталога) → назначение ролей
администратором → **повторный вход**, потому что смена ролей рвёт сессии пользователя.
Администратора скрипт не трогает, иначе потерял бы права посреди прогона.

## Сквозные сценарии этапа 5 (уведомления, сроки, правила сортировки)

Проверяют на живом стенде то, чего не видно в юнитах: `test_stage5_notifications.mjs` — назначение →
уведомление исполнителю → бейдж → прочтение, сроки `за N дней / сегодня / просрочка`, отчёт и закрытие
гасят напоминания, чужое уведомление недоступно (404), без права — 403, карта ссылок `LINK_BY_KIND`
целиком (8 видов), А9 `/deadline-presets`; `test_stage5_sorting.mjs` — правило ставит метку, приоритет
и подсказку, поднимает письмо в очереди, `rulesOnly`/`sort=rules`, предпросмотр, и **не создаёт документ
и не тратит номер** (сверяется `next-number` и `total` журнала до/после).

⚠️ **Защиту проверяют инъекцией дефекта, а не чтением кода.** Три обязательные инъекции этапа 5:
снятие `requirePermission("notifications.view")` (краснеют `routes.access` + матрица ролей),
снятие фильтра `user_id` в `markNotificationRead` (краснеет IDOR-тест уровня данных; серверные моки
этот дефект НЕ ловят), «правило регистрирует документ» (краснеет `notifications.routes`).
Порядок: sha256 до → правка → прогон (обязан быть красным) → откат → sha256 после совпал → прогон зелёный.

## Грабли, которые уже ломали проверку

- **Тесты и рабочий экземпляр делят базу** — прогон вычищает настройки стенда. Для тестов отдельная
  база (`mailsense_test`), адрес — `DOCFLOW_TEST_DATABASE_URL`.
- ⚠️ **Два параллельных jest-прогона на общей базе дают ложные падения**: `deadlock detected` и
  `duplicate key documents_period_number_idx`. Окно на PostgreSQL выдаётся явно, по одному владельцу
  (проверено 2026-10-07: 12 и 31 «провал» были именно этим, а не кодом). Перед разбором красного
  сначала проверьте `pg_stat_activity`, а не ищите дефект в коде.
- ⚠️ **Тест, который зависит от состояния, оставленного другим файлом, — не тест.** Файл, который пишет
  в общую базу, обязан убирать за собой (`afterAll` + ассерт уборки), а тест схемы — не полагаться на
  «в базе пусто», а сам приводить состояние (TRUNCATE + переигровка миграции). Так этап 5 получил
  зелёный статус только после починки: до неё `notifications.schema.test.ts` краснел от порядка файлов.
- **На Windows SQLite-файл не удаляется, пока открыт**: в `afterAll` сначала `closeDb()`,
  потом `fs.rmSync` в `try/catch`.
- **Тесты на сокетах нужно закрывать принудительно**: `--testTimeout` + `--forceExit`, а в тесте
  уничтожать оставшиеся соединения перед `server.close()` — иначе прогон висит.
- **`res.json()` принимает `any`**: забытый `await` не ловится компилятором и уходит клиенту как `{}`.
  Для асинхронных репозиториев docflow это отдельная зона внимания.
- **«Думающие» модели ИИ не годятся для summary**: возвращают пустой ответ. Проверять модель коротким
  запросом с `json_object` до настройки.
- ⚠️ **Скрипт проверки может врать сильнее, чем код.** Один раз почти отчитались о баге в продукте,
  которого не было: проверочный скрипт передавал `mail.id` вместо `mail.emailId` и регистрировал
  документы без связи с письмом. Разрешил вопрос **прямой запрос в базу**, а не чтение кода.
- ⚠️ **Кнопка «Обработать» в браузере должна быть настоящей кнопкой.** Проверяйте, что клик привёл
  к смене экрана, а не просто «ничего не упало»: ссылки на элементы живут только внутри одного снимка,
  поэтому искать и кликать нужно в одной программе.
- ⚠️ **Сборка SPA требует доступа шире песочницы**, а разрешение выдаётся **на вызов команды**:
  вложенные инструменты сохраняют собственную политику. См. `build.md`.
