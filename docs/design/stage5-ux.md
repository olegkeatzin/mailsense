### 1.3 Склонения: готовая функция (копировать в код дословно)

Русские склонения — источник опечаток вроде «осталось 1 дней». Функция одна на весь этап.

```ts
/** Русская форма слова после числа: 1 день, 2 дня, 5 дней. */
export function dayWord(n: number): string {
  const abs = Math.abs(n) % 100;
  const last = abs % 10;
  if (abs > 10 && abs < 20) return "дней";
  if (last === 1) return "день";
  if (last >= 2 && last <= 4) return "дня";
  return "дней";
}

/** «остался 1 день», «осталось 2 дня», «осталось 5 дней». */
export function daysLeftText(n: number): string {
  return (n === 1 ? "остался " : "осталось ") + n + " " + dayWord(n);
}

/** «просрочено на 1 день», «просрочено на 2 дня», «просрочено на 5 дней». */
export function overdueText(n: number): string {
  const d = Math.abs(n);
  return "просрочено на " + d + " " + dayWord(d);
}
```

Проверочные значения (должны быть в тесте): 1 → «день», 2 → «дня», 4 → «дня», 5 → «дней»,
11 → «дней», 21 → «день», 22 → «дня», 25 → «дней», 101 → «день», 111 → «дней».

### 1.4 Время в списке уведомлений: готовая функция

Относительное время — до суток, дальше абсолютное. Часовой пояс берём системный (как везде в SPA),
никакого UTC-сдвига руками.

```ts
/** «только что», «5 минут назад», «2 часа назад», «вчера, 14:05», «07.10.2026, 14:05». */
export function notificationTime(iso: string, now: Date = new Date()): { label: string; exact: string } {
  const d = new Date(iso);
  const exact = d.toLocaleString("ru-RU", {
    day: "2-digit", month: "2-digit", year: "numeric", hour: "2-digit", minute: "2-digit"
  });
  if (isNaN(d.getTime())) return { label: "", exact: "" };
  const diffMin = Math.floor((now.getTime() - d.getTime()) / 60000);
  if (diffMin < 1) return { label: "только что", exact };
  if (diffMin < 60) return { label: diffMin + " " + minuteWord(diffMin) + " назад", exact };
  const diffH = Math.floor(diffMin / 60);
  if (diffH < 24) return { label: diffH + " " + hourWord(diffH) + " назад", exact };
  const yesterday = new Date(now);
  yesterday.setDate(now.getDate() - 1);
  const sameDay = (a: Date, b: Date) => a.toDateString() === b.toDateString();
  if (sameDay(d, yesterday)) {
    return { label: "вчера, " + d.toLocaleTimeString("ru-RU", { hour: "2-digit", minute: "2-digit" }), exact };
  }
  return { label: exact, exact };
}

function minuteWord(n: number): string {
  const l = n % 10, a = n % 100;
  if (a > 10 && a < 20) return "минут";
  if (l === 1) return "минуту";
  if (l >= 2 && l <= 4) return "минуты";
  return "минут";
}
function hourWord(n: number): string {
  const l = n % 10, a = n % 100;
  if (a > 10 && a < 20) return "часов";
  if (l === 1) return "час";
  if (l >= 2 && l <= 4) return "часа";
  return "часов";
}
```

- Видимая подпись — `label`, полное время — в `Tooltip title={exact}` и в `title` элемента.
- В тестах: 30 секунд → «только что»; 1 мин → «1 минуту назад»; 2 мин → «2 минуты назад»;
  4 мин → «4 минуты назад»; 5 мин → «5 минут назад»; 11 мин → «11 минут назад»;
  21 мин → «21 минуту назад»; 22 мин → «22 минуты назад»; 59 мин → «59 минут назад»;
  1 час → «1 час назад»; 3 часа → «3 часа назад»; 11 часов → «11 часов назад»;
  21 час → «21 час назад»; 23 часа → «23 часа назад»; вчера → «вчера, HH:mm».
- ⚠️ Исправлено 2026-10-07 (нашёл frontend-dev): прежняя версия `minuteWord` знала две формы
  (`n % 10 === 1 ? "минуту" : "минуты"`) и давала «5 минуты назад», «59 минуты назад». У минут,
  как и у часов, **три** формы: 1 минуту / 2–4 минуты / 5+ минут, с исключением 11–14.

### 1.5 Доступность: общие требования (детали — §6)

- Всё интерактивное — `<button>`/Ant-компоненты, а не `<div onClick>`. Фокус виден, `outline` не убираем.
- Иконка без текста — `aria-label`; счётчик — `aria-label` словами, а не только цифрой.
- `Esc` закрывает панель/модалку и возвращает фокус туда, откуда открыли.
- Единственная `aria-live`-зона на приложение — счётчик непрочитанных (вежливое объявление).
- Тексты ошибок и пустых состояний — не только цветом: иконка + слово + действие.

### 2.2 Панель

**Решение: `Popover` (не `Drawer`).** Панель привязана к колокольчику, живёт в одном месте
экрана, не перекрывает рабочее место аппарата и совпадает по модели с уже используемым
`Dropdown` в `CurrentUser`. Ширина **380px**, но не больше `92vw`; список —
`maxHeight: 420`, прокрутка только внутри списка; шапка панели не прокручивается.

```tsx
<Popover
  open={panelOpen}
  onOpenChange={setPanelOpen}
  trigger="click"
  placement="bottomRight"
  arrow={false}
  content={<NotificationsPanel onClose={() => setPanelOpen(false)} />}
/>
```

Внутри панели — `role="dialog"`, `aria-label="Центр уведомлений"`, `aria-modal={false}`,
контейнер с `tabIndex={-1}` и `ref`:

- при открытии фокус переходит на контейнер панели (`afterOpenChange`), а не остаётся на колокольчике;
- `Esc` закрывает панель и возвращает фокус на колокольчик;
- `Tab` идёт по порядку: «Прочитать все» → «Только непрочитанные» → элементы списка →
  «Показать ещё» → сноска о хранении.

Состав (сверху вниз):

1. **Шапка.** `Уведомления` (шрифт 14, вес 600) + `<Badge count={unread} size="small" style={{backgroundColor:"#cf1322"}} />`;
   справа `<Button size="small" disabled={unread === 0}>Прочитать все</Button>`.
   При `unread === 0` кнопка показана, но недоступна (не исчезает — иначе шапка «прыгает»).
2. **Фильтр.** `<Checkbox>Только непрочитанные</Checkbox>` — это фильтр-состояние, поэтому
   `Checkbox`, а не `Switch` (переключатель читался бы как «режим приложения»). Включение фильтра
   шлёт **серверный** запрос `GET /notifications?limit=20&unread=1`: фильтрация уже загруженных
   20 записей спрятала бы непрочитанное 21-е и показала ложное «Непрочитанных нет».
   Снятие фильтра перечитывает список без `unread`.
3. **Список** (см. §2.3).
4. **Футер.** Если `items.length < total` — `<Button type="link">{Показать ещё}</Button>` и
   счётчик `Показаны 20 из 137`. Если `total >= 100` — сноска 12px `#595959`:
   `Хранятся последние 500 уведомлений: прочитанные старше удаляются автоматически.`

### 2.3 Элемент списка

Один элемент — `<button type="button">` во всю ширину (без своей рамки, hover `#fafafa`,
focus — стандартное кольцо Ant), внутри:

```
[иконка severity]  Заголовок уведомления                    • 5 минут назад
                   Текст в две строки, дальше многоточие…
```

| Часть | Правило |
|---|---|
| Иконка severity | `info` → `InfoCircleOutlined` `#0958d9`; `warning` → `WarningOutlined` `#ad4e00`; `danger` → `ExclamationCircleOutlined` `#cf1322`. У иконки `aria-hidden`, смысл несёт текст |
| Заголовок | 14px, вес 600 у непрочитанного, 400 у прочитанного, одна строка, `ellipsis` |
| Текст (`body`) | 13px `#595959`, максимум 2 строки (`-webkit-line-clamp: 2`); пустой `body` — строку не рисуем вовсе |
| Время | 12px `#767676`, `notificationTime(createdAt).label`, `Tooltip` с `exact` |
| Непрочитанное | маркер-точка `•` `#cf1322` **и** скрытый текст `непрочитано` (`.visually-hidden`) |
| Длинная строка | `overflow-wrap: anywhere` — тема письма и ФИО бывают без пробелов |

`aria-label` элемента собирается целиком, чтобы скринридер не читал «звёздочку»:

```ts
// «Уведомление: Вам поручение. Срок 07.10.2026. 5 минут назад. Непрочитано.»
const aria = "Уведомление: " + n.title + (n.deadline ? ". Срок " + fmt(n.deadline) : "")
  + ". " + time.label + (n.readAt ? "" : ". Непрочитано.");
```

Элемент с `link === null` (уведомление без раздела) — **не** кнопка-переход, а блок с отдельной
кнопкой `<Button size="small" type="link">{markRead}</Button>` и `aria-label`
`Отметить уведомление прочитанным: {title}`. Иначе клик по «ничему» обещает переход, которого нет.

### 2.4 Состояния панели

| Состояние | Как выглядит | Тексты |
|---|---|---|
| Загрузка (первая) | `Skeleton` 3 строки, `aria-busy="true"`, `aria-label={loading}` | `Загрузка уведомлений` |
| Загрузка «ещё» | кнопка «Показать ещё» в `loading`, список не исчезает | — |
| Пусто (всего 0) | `Empty` с `BellOutlined` серым | `Уведомлений пока нет` / `Здесь появятся поручения, сроки и решения по вашим документам.` |
| Пусто при фильтре | `Empty` | `Непрочитанных нет` / `Все уведомления прочитаны.` + кнопка `Показать все уведомления` (снимает фильтр) |
| Ошибка загрузки | `Alert type="error" showIcon` | `Не удалось загрузить уведомления` + текст ошибки + кнопка `Повторить` |
| Ошибка отметки прочитанным | `message.error` (коротко, панель не рушим) | `Не удалось отметить уведомление прочитанным: {текст}` |
| «Прочитать все» успешно | `message.success` | `Все уведомления прочитаны` |

Оптимистично: клик по элементу сразу красит его прочитанным (локально), затем `POST /read`;
при ошибке — откат и `message.error`. Счётчик уменьшается сразу — иначе бейдж «залипает».

### 2.5 0 уведомлений и 100+ — поведение

- **0:** бейдж скрыт; панель открывается и честно говорит `Уведомлений пока нет`. Никаких
  «нет новых уведомлений» без пояснения — человеку нужно знать, где они появятся. Опрос
  `/count` продолжается (иначе первое уведомление не появится до перезагрузки).
- **1…99:** бейдж с числом; список отдаёт до 20 записей, «Показать ещё» добавляет по 20.
- **100 и больше:** бейдж `99+` (в `aria-label` — словами); в панели — первые 20 и
  `Показаны 20 из 137`. Внизу сноска о хранении 500 записей. Пустого экрана и «вечной
  прокрутки» не делаем: у панели фиксированная высота списка.
- **500+ в базе не бывает** (сервер чистит прочитанные), поэтому интерфейс не рисует пагинацию
  страницами.

### 2.6 Роль без права `notifications.view`

- Колокольчик **не рендерится вовсе** — ни бейджа, ни `Tooltip`, ни пустой кнопки.
  Это не «эстетика»: `/count` без права отвечает 403, и правило §7 контракта требует
  пустой консоли у каждой роли. Скрытая кнопка без запроса — единственный способ.
- Опрос `/count` не запускается: проверка `if (!can("notifications.view")) return;` до `setInterval`.
- Если право отозвали в текущей сессии — на 401/403 таймер **останавливается** и повторно не
  поднимается (`failedAuth` флаг), панель не открывается. Ретраить 403 каждую минуту нельзя.
- Право добавляется в `types.ts` (`Permission`) и в матрицу прав; UI только прячет, решает сервер.

### 2.6а Выключатель: `enabled` приходит в данных (А4)

`enabled: boolean` отдают и `GET /notifications`, и `GET /notifications/count` (Приложение А, А4).
Поэтому «пусто» бывает двух разных смыслов, и панель обязана их различать:

| Условие | Заголовок | Текст |
|---|---|---|
| `enabled === true`, уведомлений нет | `Уведомлений пока нет` | `Здесь появятся поручения, сроки и решения по вашим документам.` |
| `enabled === false` | `Уведомления отключены администратором` | `Уже полученные уведомления остались — их можно прочитать. Новые не создаются.` |

Колокольчик при `enabled === false` **остаётся**: непрочитанные, созданные до выключения, читать
можно, и прятать их было бы потерей данных. Опрос `/count` продолжаем — админ может включить
обратно, а вызов дешёвый.

### 2.7 Опрос счётчика

- `GET /api/docflow/notifications/count` раз в **60 с**, только при `can("notifications.view")`.
- Пропуск тика, если `document.hidden`; при возврате на вкладку — немедленный `poke()`
  (образец уже есть — `utils/progressPolling.ts`, повторно использовать, а не писать третий таймер).
- `clearInterval` + сброс флага на размонтировании. Гонка: ответ на запрос, начатый до
  `markAll`, не должен вернуть старый счётчик — хранить монотонный `requestId` и применять
  только последний (в проекте такая гонка уже ловилась).
- Панель обновляет список действием `loadNotifications`; отдельного таймера на список нет.
- Ошибки опроса не шумят в консоль: `catch` → тихо, счётчик остаётся прежним.

## 3. Состояния срока в «Моих задачах» и канбане

### 3.1 Модель состояний (единственная на оба экрана)

Считаем только по данным сервера: `daysLeft` (может быть `null`) и `overdue`. Своих вычислений
«сегодня» в интерфейсе нет — иначе часовой пояс и рабочие дни разъедутся с сервером.
Порог «скоро» настраивается администратором (`dueSoonDays`, по умолчанию 3) и **приходит в
данных**: `TaskItem.dueSoon: boolean` сервер считает по тому же порогу, что и уведомление
`resolution.due_soon` (Приложение А, А5). Поэтому:

- плашку «осталось N дней» показывает `dueSoon === true`; интерфейс **не сравнивает `daysLeft`
  с числом** и не держит своей константы порога — константа `DISPLAY_DUE_SOON_DAYS` из первой
  редакции этого документа удалена;
- `daysLeft`, `overdue`, `dueSoon` — только с сервера, без локальных вычислений «сегодня»;
- канбан получает **те же** признаки: `ResolutionDetail.daysLeft: number | null` и
  `ResolutionDetail.dueSoon: boolean` (Приложение А, А11) — состояния на карточке считаются
  по ним, а не по локальному порогу.

| Условие | Видимый текст | Цвет | `Tag` | `aria-label` плашки |
|---|---|---|---|---|
| `daysLeft < 0` | `просрочено на 5 дней` | `#cf1322` | `color="red"` (5.07:1) | `Срок просрочен на 5 дней` |
| `daysLeft === 0` | `срок сегодня` | `#ad4e00` | свой `style` (5.09:1) | `Срок сегодня` |
| `dueSoon === true` (порог задан настройкой) | `остался 1 день` / `осталось 2 дня` / `осталось 5 дней` | `#ad4e00` | свой `style` | `До срока остался 1 день` |
| `dueSoon === false` | плашки нет, только дата | `#262626` | — | `Срок 07.10.2026` |
| `deadline === null` | `не указан` (задачи) / `без срока` (канбан) | `#595959` | `<Tag>` у канбана | `Срок не указан` |
| закрыто / есть отчёт | как «дальний срок»: дата без плашки | `#262626` | — | — |

Tag срока — **свой `style`, не пресет** `color="orange"` (пресет даёт 3.34:1):

```tsx
const SOON_STYLE = { color: "#ad4e00", background: "#fff7e6", borderColor: "#ffd591" };
// просрочка — можно пресетом: <Tag color="red">…</Tag>
```

Компонент `DeadlineTag` (один на два экрана) — пропсы
`{ deadline: string | null; daysLeft: number | null; overdue: boolean; variant: "table" | "card" }`,
дата — `dayjs(deadline).format("DD.MM.YYYY")`, текст — из §1.3.

### 3.2 «Мои задачи» (`MyTasks.tsx`), колонка «Срок»

Сейчас (строки 111–136) порог `<= 3` зашит в код и `Tag color="orange"` не проходит контраст.
Целевой вид:

| Ситуация | Ячейка |
|---|---|
| нет срока | `<span style={{color:"#595959"}}>не указан</span>` (оставляем) |
| дальний срок | дата, `#262626` |
| скоро | дата + `<Tag style={SOON_STYLE}>осталось 5 дней</Tag>` |
| сегодня | дата (вес 600) + `<Tag style={SOON_STYLE}>срок сегодня</Tag>` |
| просрочено | дата `#cf1322` вес 600 + `<Tag color="red">просрочено на 5 дней</Tag>` |

Кнопка «В календарь» остаётся как есть (Р11) — единственный путь напоминания вне приложения.
Шапка раздела: `Мои задачи` + `<Badge count={overdue} style={{backgroundColor:"#cf1322"}} />` +
слово `просрочено` (текст уже есть, оставляем: цвет не единственный носитель).

### 3.3 Канбан (`ResolutionBoard.tsx`), карточка

В строке тегов карточки: номер, приоритет, срок. Целевой вид тега срока:

| Ситуация | Тег на карточке |
|---|---|
| нет срока | `<Tag color="orange">без срока</Tag>` → **чиним** на `<Tag style={{color:"#ad4e00",background:"#fff7e6",borderColor:"#ffd591"}}>без срока</Tag>` |
| дальний срок (`dueSoon === false`) | `<Tag>{дата}</Tag>` (как сейчас), цвет `#262626` |
| скоро (`dueSoon === true`, `daysLeft > 0`) | `<Tag style={SOON_STYLE}>{дата} · осталось 2 дня</Tag>` |
| сегодня (`daysLeft === 0`) | `<Tag style={SOON_STYLE}>{дата} · срок сегодня</Tag>` |
| просрочено (`daysLeft < 0`) | `<Tag color="red">{дата} · просрочено на 5 дней</Tag>` |

Приложение А, А11: `ResolutionDetail` отдаёт `daysLeft: number | null` и `dueSoon: boolean` —
те же, что у `TaskItem`, и тот же порог `notifications.dueSoonDays`. Поэтому канбан показывает
полные состояния, а не только дату:

- порога-константы в `ResolutionBoard.tsx` нет: сравнения — только с нулём (`daysLeft < 0` —
  просрочка, `daysLeft === 0` — сегодня) плюс флаг `dueSoon`; «за сколько дней» решает сервер;
- тексты и цвета — из §3.1, через один `DeadlineTag` (`variant="card"`): `осталось 2 дня` /
  `срок сегодня` / `просрочено на 5 дней` — те же слова, что в «Моих задачах»;
- при `deadline === null` — прежний тег «без срока»;
- в колонке «Просрочено» карточка получает `daysLeft < 0` и показывает то же число, что и
  «Мои задачи» — расхождения между экранами быть не должно.

Отдельная колонка «Просрочено» остаётся (в ней смысл всего канбана). Внутри колонки
карточка дублирует плашку — это нормально: колонку видно издалека, плашку читают в карточке.
Текст «пусто» в колонке: `#595959` вместо `#767676` (4.35:1 → 6.71:1 при 12px).

### 3.4 Порог «за N дней»

- Порог меняет администратор во вкладке «Уведомления» (§5.2). Интерфейс задач ничего не
  переключает: он показывает `daysLeft`/`overdue`/`dueSoon` с сервера (Приложение А, А5;
  для канбана — А11).
  Локальных порогов в коде нет — искать «3» в `MyTasks.tsx` после правки бессмысленно.
- Если срок продлили, а плашка осталась «просрочено» — перечитываем список (у `MyTasks` уже
  есть `load()`). Значения `daysLeft`/overdue с сервера считаются на чтении, клиент их не кэширует.

### 3.5 Что чиним попутно в этих двух файлах

1. `MyTasks.tsx`: `daysLeft <= 3` → порог от сервера/единый `DeadlineTag`; `Tag color="orange"` → `SOON_STYLE`.
2. `MyTasks.tsx`: `<Tag color="green">сдан …</Tag>` — 3.37:1, заменить на
   `<Tag style={{color:"#237804", background:"#f6ffed", borderColor:"#b7eb8f"}}>` (проверить тестом; `#237804` на `#f6ffed` — норма проходит).
3. `ResolutionBoard.tsx`: `Tag color="orange"` для «без срока» → `SOON_STYLE`; `#767676` → `#595959`.

### 3.6 Типовые сроки в форме резолюции (А9)

Где: `components/ResolutionModal.tsx`, под полем «Срок» — это `DatePicker` с `format="DD.MM.YYYY"`,
который хранит строку `YYYY-MM-DD`. Логика выносится в новый
`components/DeadlinePresets.tsx`, чтобы модалка (256 строк) не разрасталась.

**Данные.** `GET /api/docflow/deadline-presets` (право `resolution.create`) →
`{ workdayDeadlines: boolean; holidays: string[]; items: [{ id, title, days, isWorkday, dueDate }] }`.

- Запрос — один раз при открытии модалки (`open === true`), не на каждый ввод символа.
  Ответ применяем, только если модалка ещё открыта: иначе гонка и `setState` после закрытия.
- `from` **не передаём**: по контракту А9 сервер сам подставляет сегодняшнюю дату. Параметр
  нужен, только когда база отсчёта — не сегодня (например, дата письма): тогда `?from=ГГГГ-ММ-ДД`.
  ⚠️ В постановке было `?from=<сегодня>`; клиентское «сегодня» — это вычисление даты на клиенте,
  которого мы договорились не делать, и на границе суток оно разойдётся с сервером. Нужно именно
  клиентское значение — скажи, зафиксирую его явно.
- `dueDate` — **только серверная**: клиент её не считает, не округляет и не перепроверяет.
  Если `dueDate` пустой или отсутствует — чип не рисуем (подставлять нечего).
- Праздники в интерфейсе не перечисляем: они уже учтены в `dueDate`. Показать их здесь —
  приглашение пересчитывать сроки руками.

**Вид** (под полем «Срок»):

```
Срок  [ 10.10.2026 ▾ ]   не указан — подсветится аппарату
Типовые сроки:  (3 рабочих дня — 10.10.2026)  (10 рабочих дней — 21.10.2026)  (30 календарных дней — 09.11.2026)
```

- Подпись чипа: `{title} — {dueDate в ДД.ММ.ГГГГ}`. Названия — из `title` как есть
  («3 рабочих дня», «30 календарных дней»); своих сокращений и своих расчётов не сочиняем.
- Префикс `Типовые сроки:` — 12px `#595959`, часть строки, а не отдельный заголовок.
- Чип — `<Button size="small">`, а не `<Tag onClick>`: `Tag` не берёт фокус и недостижим с
  клавиатуры. `aria-label` чипа: `Подставить срок 10.10.2026 по подсказке «3 рабочих дня»`;
  группа — `role="group"` + `aria-label="Типовые сроки"`.
- Клик: `setDeadline(item.dueDate)`. Поле остаётся обычным `DatePicker` — человек может выбрать
  любую другую дату, чипы только подставляют. Тост не показываем: значение видно в поле.
- `workdayDeadlines === false` → под чипами 12px `#595959`:
  `Рабочие дни выключены в настройках: сроки считаются в календарных днях.`

**Состояния:**

| Состояние | Вид | Текст |
|---|---|---|
| Загрузка | 3 × `Skeleton.Button size="small" active`, у группы `aria-busy="true"` | — (скелетоны вместо надписи: строка не «прыгает») |
| Пусто (`items: []`) | **ничего не рисуем** — ни префикса, ни плейсхолдера | — |
| Ошибка загрузки | `Alert type="error" showIcon` | `Не удалось загрузить типовые сроки` / `Срок можно ввести вручную — сохранение резолюции это не блокирует.` + кнопка `Повторить` |
| Нет права `resolution.create` | чипов нет, запроса нет (форма резолюции недоступна) | — |

Ошибка ничего не блокирует: кнопки `Сохранить черновик` и `Отправить на утверждение` остаются
активными, срок можно ввести руками или оставить пустым.

**Что НЕ делаем:** CRUD справочника типовых сроков (§8), локальный пересчёт при переключении
настройки «рабочие дни» (её читает сервер; новое значение применится при следующем открытии формы),
свой календарь праздников в этой модалке.

## 4. «Входящие на регистрацию» (`IncomingList.tsx`)

Главный принцип раздела не меняется: **письмо размечает аппарат, документ регистрирует человек.**
Правило сортировки только помогает глазами — метка, подсказка, приоритет, место в очереди.

### 4.1 Шапка раздела

```
Входящие на регистрацию · 18                     [Только по правилам]  [По дате | По правилам]  [В журнал] [Обновить]
Документ регистрирует человек: правило только помечает письмо меткой и подсказкой
и поднимает его в очереди. Номер при этом не выдаётся.
```

### 4.2 Чипы правил и подсказка

Порядок внутри `<Space size={4} wrap>` карточки: сначала существующие (внешний номер, дата,
вложения, теги анализа, статус анализа), затем блок правил:

| Поле | Вид | Текст/Tooltip |
|---|---|---|
| `sortLabels[]` | `<Tag color="blue" icon={<TagOutlined />}>{label}</Tag>` | Tooltip `Метка правила сортировки` |
| `sortPriority` ≠ null | `<Tag icon={<FlagOutlined />} style={SOON_STYLE}>правило: Высокий</Tag>` | Tooltip `Приоритет предложен правилом сортировки`; подпись — `priorityLabel(p)` из `utils.ts` (1 «Очень низкий» … 5 «Очень высокий»), а не `PRIORITY_TITLES` (те про 3 уровня резолюции) |
| `sortNotes[]` | `<Alert type="info" showIcon message="Подсказка правила" description={notes.join(" ")} />` под тегами | не сворачиваем: подсказка и есть смысл правила |
| `sortMatched` | отдельного чипа нет | видно по меткам; нужен фильтру |

`Tag color="blue"` — 5.50:1, норма проходит. `purple` (6.26:1) — резерв, если метку надо
отличить от «внешнего номера»; выбираем **blue**, потому что `purple` в проекте уже занят под
теги анализа писем.

Tooltip на чипе метки обязателен: сам по себе чип «Прокуратура» не говорит, откуда он.

| `total > items.length` | под списком 12px `#595959` | `Показаны первые 300 из 340. Уточните фильтр или обновите список.` |

Почему не «Показать ещё»: Приложение А, А6 — `offset` вне этапа, список ограничен
`limit ≤ 300`. Придумывать параметр нельзя (Hyrum's law и заморозка), поэтому честная подпись
«показаны первые N из total» плюс предложение уточнить фильтр. Если контракт расширят — добавим
«Показать ещё».

### 4.5 Метки не дают права регистрировать

Кнопка «Зарегистрировать» не меняется: правило не может её ни убрать, ни добавить,
ни открыть форму автоматически. Никаких «Зарегистрировать по правилу» — см. §8.

Textarea, а не календарь: дат до сотни, а модалка 760px — календарь в ней не поместится.
Перед `PUT` строки обрезаем, пустые выбрасываем, дубликаты и порядок приводит сервер — клиент
лишь не отправляет заведомый мусор. Ошибку 400 показываем текстом сервера, модалку не закрываем.

**4. Тексты уведомлений (блок шаблонов)**

Таблица: `Вид` | `Заголовок` | `Состояние` | `Действия`.

Расшифровка `kind` → русская подпись (только интерфейс, `kind` заморожен §3):

```ts
export const NOTIFICATION_KIND_TITLES: Record<string, string> = {
  "resolution.assigned": "Вам поручение",
  "resolution.approved": "Резолюция утверждена",
  "resolution.reported": "По поручению отчитались",
  "resolution.closed": "Поручение закрыто",
  "resolution.due_soon": "Приближается срок",
  "resolution.due_today": "Срок сегодня",
  "resolution.overdue": "Срок просрочен",
  "resolution.overdue_escalation": "Просрочка у исполнителя"
};
```

- `Заголовок` — текст шаблона, одна строка с `ellipsis`, полный текст в `Tooltip`.
- `Состояние` — `<Tag>выключен</Tag>` при `isActive === false`, иначе пусто.
- `Действия` — `Изменить` (модалка: `Input` заголовка + `Input.TextArea rows={4}` текст;
  кнопки `Сохранить` / `Отмена`; успех — `message.success("Шаблон сохранён")`).
- **Список переменных — с сервера** (Приложение А, А2): `GET /notifications/settings` отдаёт
  `variables: { key, title }[]`. Интерфейс **не хардкодит список**: рисует чипы из ответа, а клик
  по чипу вставляет `{key}` в текст (`aria-label` — `Вставить {regNumber}`). Подсказка к полю:
  `Доступные подстановки: ` + перечисление `title` через запятую.
- Неизвестная переменная **остаётся в тексте как есть** — так решено в контракте: видно ошибку,
  а не тихую пустоту. Рендер уведомления — плоский текст, без HTML.
- Пояснение к модалке: `Сервер подставит данные поручения в фигурные скобки. Если переменная написана неверно, она останется в тексте как есть.`
- Пусто: `Empty description="Шаблоны уведомлений не загружены"` + `Повторить`.
- Загрузка: `Skeleton` 4 строки; ошибка: `Alert type="error"` `Не удалось загрузить настройки уведомлений` + `Повторить`.

**Сохранение блока 1–3** — одна кнопка `Сохранить настройки` (`type="primary"`), `loading`,
`PUT /notifications/settings`; успех `message.success("Настройки уведомлений сохранены")`,
ошибка `Alert type="error"` `Не удалось сохранить настройки` + текст сервера. Шаблоны
сохраняются отдельно (у них своя модалка) — смешивать в одном PUT нельзя, у него нет полей шаблонов.

### 5.3 Права

- Вкладки `sorting`/`notifications` рисуются только при `can("settings.manage")`.
- Запросы `/sorting/rules*` и `/notifications/settings` не отправляются, пока вкладка не открыта
  и права нет. Прятать кнопки мало — 403 в консоли проверяется приёмкой.
- Ответ `403` на любом из этих маршрутов: `Alert` с текстом `Недостаточно прав для этого раздела`
  (без повторов и без автоматического ретрая).
- Ошибка `404` при `PATCH/DELETE` правила (его удалил другой админ) — `message.error("Правило уже удалено. Обновите список.")` + перечитать таблицу.

## 8. Что НЕ рисуем (проверяется на приёмке)

1. **Писем-напоминаний нет.** Ни кнопки «Отправить напоминание», ни «продублировать письмом»,
   ни колонки «напоминание отправлено», ни настроек SMTP для уведомлений. Единственный
   внешний путь — «В календарь» (.ics), он уже есть (Р11, контракт §0.1).
2. **Авторегистрации нет.** Ни переключателя «регистрировать автоматически», ни «правило создаёт
   документ», ни «занять номер», ни автозаполнения формы регистрации правилом, ни возврата
   авторазбора. Правило не выдаёт номер ни при каких настройках (rules §6.1, контракт §0.2).
3. **Никаких браузерных push-уведомлений** (`Notification API`) и звуков — в контракте их нет.
4. **Нет отдельной страницы уведомлений** и новых `AppSection`: только панель.
5. **Нет drag&drop** порядка правил, нет графа знаний, нет смены формата номера (вне этапа, §0).
6. **Нет «напоминаний о сроке» в интерфейсе администратора** в виде рассылки: только порог N дней.
7. **Нет обещаний в текстах**, которых не выполняет сервер: слова «система зарегистрирует»,
   «письмо будет создано автоматически», «напомним письмом» — запрещены в любых подписях.
8. **Справочника типовых сроков (CRUD) нет** — вне этапа 5 (А9). В форме резолюции только
   чипы-подсказки с серверной датой; ручной ввод срока остаётся как есть.
