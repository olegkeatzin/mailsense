# План: Electron-клиент + сервер СЭД (вариант А)

Решение заказчика (2026-10-07/08). Кратко: **один вход — Electron-приложение** у каждого сотрудника,
**docker-сервер** держит СЭД и служебные ящики аппарата. Браузерный вход отложен.

## Зафиксированные решения

1. **Топология.** Electron-клиент на машине пользователя (окно + локальный backend) + сервер СЭД
   (docker: PostgreSQL, журнал, резолюции, аудит). Браузерного входа пока нет.
2. **Почта — на сервере** (вариант А). На сервере живут **два служебных ящика аппарата**:
   внешний (приёмный, напр. `manufactory@kaluga.net`) и внутренний (делопроизводство, напр. `post@mail.test`).
   Личные ящики сотрудников приложение не читает (Р3) и на сервер не попадают.
3. **Клиент становится тонким и для почты.** Эксперимент показал: сейчас `/api/docflow/*` идёт на сервер,
   а почтовые пути клиент обслуживает сам — в результате аппарат видел бы очередь писем, которые не может
   открыть (очередь с сервера, письма локальные). Поэтому почтовые пути тоже проксируются на сервер.
4. **Личные настройки работника — локально** в клиенте: отображаемое имя отправителя, подпись, шаблоны,
   черновики, параметры ответа/цитирования. На сервер эти данные не уезжают. Плата за это: на другом
   компьютере и после переустановки личные настройки придётся завести заново (осознанно).
5. **Подпись работника.** Письмо уходит с адреса служебного ящика, но в `From` стоит имя работника
   («Иванов И.И., аппарат»). Сейчас имя берётся из настроек ЯЩИКА (sendService.ts:62-64) — на общем ящике
   все подписывались бы одинаково.
6. **Ответ — с того ящика, куда пришло письмо.** Ответ на внешнее письмо уходит с внешнего ящика,
   `Reply-To` = тот же внешний ящик. Письмо руководителю и исполнителям уходит всегда с внутреннего.
7. **POP3 обязателен в проде** (IMAP есть не везде). Приложение писем с сервера не удаляет (нет `DELE`,
   только UIDL/RETR), «Отправленные» ведёт локальной копией при отправке.
8. **Адрес сервера — из конфига предприятия**, вложенного в раздаваемый zip: сейчас он читается только
   из профиля пользователя, поэтому «распаковал → поправил → запаковал» не работает.

## Схема

```
машина сотрудника                          сервер (docker)
┌──────────────────────────────┐           ┌─────────────────────────────────┐
│ Electron: окно (SPA)         │  HTTP +   │ /api/auth /api/docflow ...      │
│ локальный backend 127.0.0.1  │  cookie   │ PostgreSQL: журнал, резолюции,  │
│ ├─ личные настройки, шаблоны │ ────────► │   пользователи, аудит, уведомл. │
│ ├─ черновики (локальная БД)  │           │ служебные ящики (SQLite+файлы): │
│ └─ прокси: почта + СЭД       │           │   внешний + внутренний (POP3/   │
│    (писем локально НЕТ)      │           │   IMAP, SMTP для отправки)      │
└──────────────────────────────┘           └─────────────────────────────────┘
```

## Задачи

### Т1. Тонкий клиент: прокси почтовых путей
Скоуп: `packages/server/src/proxy.ts`, тесты. Проксируем на сервер: `/api/emails`,
`/api/accounts`, `/api/threads`, `/api/analysis`, `/api/import`, `/api/compose-template`.
НЕ проксируем (остаётся локально): `/api/drafts`, `/api/templates`, личные настройки.
Настройки смешаны в одном `/api/settings` — разделить по области: личные ключи остаются локально,
служебные (`docflow.*`, `ldap.*`, `ai.*`) приходят с сервера.
**Приёмка:** клиент в режиме сервера: видит почту сервера, открывает письмо и вложение, отправляет
письмо с вложением; черновик сохраняется локально и переживает перезапуск; при недоступном сервере
почта честно говорит «сервер недоступен», а не показывает пустоту.

### Т2. Личный профиль почты (локально)
Скоуп: `packages/core` (хранилище настроек по учётке), `packages/web` (экран «Почта → Мои настройки»).
Отображаемое имя, подпись (текст/HTML, позиция), правила цитирования, шаблоны, черновики — привязка
к **учётной записи работника** (LDAP-логин), а не к ящику.
**Приёмка:** два работника аппарата за одним ящиком подписываются по-разному; шаблоны и черновики
у каждого свои; на сервере личных настроек нет (проверяется запросом к БД сервера).

### Т3. Отправка с именем работника
Скоуп: `packages/core` (sendService), `packages/server` (маршрут отправки).
- `POST /api/emails/send` принимает `fromName` и `replyTo`; адрес всегда = ящик аккаунта
  (подмена адреса — 400), имя — строка без переводов строк;
- если подпись сформирована клиентом, сервер её не добавляет повторно;
- в записи отправленного письма (и в аудите для писем по поручению) — учётка отправителя.
**Приёмка:** ответ внешнему адресату: `From: "Иванов И.И., аппарат" <manufactory@…>`,
`Reply-To: manufactory@…`; в интерфейсе/аудите видно, кто отправил; попытка подставить чужой адрес → 400.

### Т4. Две служебные почты в админке
Скоуп: `packages/docflow`, `packages/server`, `packages/web`.
Настройки: `docflow.externalAccountId` (внешний приёмный) и `docflow.serviceAccountId` (внутренний,
отправка). Вкладка «Служебные ящики»: два селектора, пояснения, валидация (ящик существует; один ящик
можно назначить на обе роли для пилота), аудит в транзакции.
Правило отправки: ответ — с ящика получения (если он служебный), пересылка руководителю и исполнителям —
с внутреннего.
**Приёмка:** письмо с внешнего ящика → ответ уходит с внешнего; руководителю — с внутреннего;
смена настроек только с `settings.manage` и попадает в аудит.

### Т5. Права на почту (бывший D-4)
Скоуп: `packages/docflow` (права), `packages/server` (маршруты), `packages/web` (скрытие разделов).
Права `mail.view` и `mail.send`; почтовые маршруты закрыты; без права почтовые разделы не показываются
и не запрашиваются. Исполнителю/подписанту/руководителю почта недоступна; письмо-источник — из карточки
задачи/документа отдельным маршрутом с проверкой связи с поручением.
**Приёмка:** исполнитель → 403 на список ящиков, чтение и отправку; при этом задача и её текст открываются;
матрица прав покрыта тестами и живой проверкой.

### Т6. Портативный адрес сервера
Скоуп: `apps/electron`, `packages/core` (чистая функция выбора), docs.
Порядок (реализовано в T37, `packages/core/src/clientConfig.ts`): `--server=` → **`server.json` рядом
с .exe** (конфиг предприятия) → `<userData>/server.json` (личная настройка) → `MAILSENSE_SERVER_URL`
(совместимости ради принимается и прежнее имя `MAILSENSE_DOCFLOW_URL`) → локальный режим.
Файл предприятия стоит ВЫШЕ переменной окружения: адрес, выданный администратором, не должен
перебиваться пользовательской настройкой. Если адрес задан политикой — в настройках read-only
«Адрес задан администратором», запись отклоняется.

⚠️ **Присутствие важнее содержимого:** если файл предприятия есть, но испорчен или адрес в нём
негодный — это ошибка старта конфигурации, а не повод искать адрес дальше. Иначе опечатка
администратора выглядела бы как «работает», а пользователь молча уехал бы на другой сервер.
Испорченный личный файл — тоже честная ошибка в журнале и в интерфейсе; приложение при этом
поднимается автономно и не падает. Поправлен неверный комментарий в `main.ts` (он утверждал,
что локальный backend не поднимается — на самом деле поднимается всегда, а сервер только проксируется).
**Приёмка:** собранный zip + `server.json` + чистый профиль → приложение сразу подключается к серверу,
пользователь вводит только логин и пароль.

### Т7. POP3 в проде
Скоуп: docs + проверки; код коннектора уже есть.
Ограничение первого скана по периоду, retention локальных копий и вложений, предупреждение «не подключайте
тот же служебный ящик в личном клиенте: POP3 забирает письма». Проверить: не удаляем письма с сервера;
дедуп по UIDL на двух ящиках; тред ответа руководителя находится и на POP3.
**Приёмка:** сквозной прогон пайплайна на POP3-ящике + раздел в `docs/mail.md` и `docs/deploy.md`.

### Т8. Сквозная приёмка на целевой топологии
На стенде: сервер + отдельный клиентский экземпляр в режиме клиента (пустой профиль) + POP3-ящик.
Прогон: внешнее письмо → регистрация → руководителю → ответ письмом → подтверждение → исполнителю →
отчёт. Проверить подпись и имя работника, локальность шаблонов/черновиков, вложения, права ролей,
пустую консоль.
**Приёмка:** отчёт с цифрами и доказательствами, как в этапе 5.

## Чего НЕ делаем сейчас

- Браузерный вход для всех сотрудников (отложен; архитектурно не мешает).
- Хранение личной почты сотрудников на сервере — противоречит цели «на сервере только служебное».
- Разделение на два репозитория/сервиса (обсуждается для 0.1.5).
- Роль «сервер только СЭД» (`MAILSENSE_ROLE=docflow`) — отменена: сервер теперь держит служебные ящики.
- CRUD справочника типовых сроков — вне объёма.

## Риски и открытые вопросы

1. **Объём вложений** при тонком клиенте: передаются данными (base64), нужен замер на реальных PDF
   и, возможно, потоковая загрузка вместо base64.
2. **Объём хранения на сервере**: почтовая SQLite + вложения растут; нужен retention и бэкап
   (тома `mailsense-data` и `mailsense-pg`).
3. **Исходящие в журнале**: ответ внешнему контрагенту сейчас в журнал не попадает — нужно решение
   заказчика, регистрировать ли исходящие автоматически или оставить ручную регистрацию.
4. **POP3 и чужие клиенты**: если тот же ящик подключён в личном клиенте с удалением после загрузки,
   сервер увидит пустой ящик. Это организационное правило, но его надо записать в deploy.
5. **Локальные личные настройки**: смена компьютера = настройки заново (принято осознанно).
