## 1. Правило для команды: служебный текст — в комментариях кода, не в разметке

1. **Служебный текст живёт только в комментариях, которые не рендерятся.**
   - вне JSX — `//` и `/* … */`;
   - внутри JSX — **только** `{/* … */}`.
2. **Между элементами JSX `//` писать нельзя.** Это не комментарий для React, а текст-ребёнок:
   именно так возник D5.

   ```tsx
   // ПЛОХО: автор думал, что это комментарий, человек видит строку в колонке
   <Tag color="green">
     сдан {dayjs(v).format("DD.MM HH:mm")}
     // Пресет green даёт 3.37:1
   </Tag>

   // ХОРОШО: либо внутри фигурных скобок, либо выше return
   {/* Пресет green даёт 3.37:1 — норма AA не проходит, поэтому свой стиль. */}
   <Tag style={READY_STYLE}>сдан {dayjs(v).format("DD.MM HH:mm")}</Tag>
   ```

3. **Технические значения не показываем сырыми.** Ключи действий, статусы, источники, виды
   уведомлений, имена полей — только через карту с русскими подписями (§3, §5).
4. **Fallback никогда не равен сырому ключу.** `MAP[x] ?? x` — запрещено;
   `MAP[x] ?? "Другое действие"` — можно. Сырой ключ в интерфейсе читается человеком как мусор.
5. **Никакого JSON и `String(объект)` в разметке.** Массивы — через запятую, объекты — «изменено»,
   `true/false` — «да/нет», `null` — «—».
6. **Английский текст допустим только как часть предметной области** (LDAP, IMAP, Base DN) и с
   русским пояснением рядом. Английское «просто так» — дефект.
7. **Текст ошибки: сначала по-русски, сырой ответ сервера — рядом, в скобках.** Молчать нельзя
   (rules §6.6), но и отдавать человеку «Failed to fetch» вместо объяснения — тоже.
8. **Задел под будущую функцию подписываем прямо:** «не реализовано», без «начнёт», «скоро»,
   «после N штук» и внутренних порогов (см. §4).

из §6. Правка интерфейса без него не принимается.

## 4. Р14 «Предложенные исполнители»: честный текст (требование заказчика)

**Что не так сейчас** (`SuggestedAssignees.tsx:52–59`):
1. «система **начнёт** подсказывать» — обещание будущей функции, а её нет;
2. «подсказка станет осмысленной примерно после 300» — внутренний порог из сервера
   (`needed: 300`), показанный как продуктовое обещание; никто не проверял, что после 300
   подсказка действительно включится;
3. `collected` подписан как «накоплено резолюций» — это честный факт, но рядом с обещанием он
   читается как прогресс-бар будущей функции.

**Готовые строки (копировать в код):**

```tsx
<Alert
  type="info"
  showIcon
  style={{ marginBottom: 12 }}
  message="Подсказка исполнителей не работает"
  description={
    <span style={{ fontSize: 12 }}>
      Система ещё не анализирует историю поручений: подсказка появится после 0.1.4, сейчас место
      в форме только зарезервировано. Накоплено резолюций: <b>{state.collected}</b>. Исполнителя
      выбирает человек.
    </span>
  }
/>
```

Правила для этого блока:
- **убрать** `needed` из текста совсем (это внутренняя величина, а не обещание);
- **оставить** `collected` — но как факт («накоплено резолюций»), а не как счётчик до включения;
- **не** употреблять «начнёт», «скоро», «в разработке», «beta» — только «не работает» и «появится
  после 0.1.4» (формулировка из `AGENTS.md`, продуктовая договорённость);
- ветка `state.ready === true` (`SuggestedAssignees.tsx:66–81`) сегодня **недостижима**: сервер
  всегда отдаёт `ready: false` (`packages/server/src/resolutionRoutes.ts:355–366`). Когда её
  включат, к заголовку обязательно добавить «предварительная подсказка, проверяйте сами» и не
  показывать `confidence` без пояснения, что это оценка, а не решение.

## 6. Расширение guard-теста `ui.noDebugText.test.tsx`

Тест хороший, но у него три слепые зоны, в которых и живут находки §3:

1. **Вкладка «Аудит» не проверяется.** Список вкладок в тесте (строка 267):
   `["Общие", "Служебный ящик", "Правила сортировки", "Уведомления"]`. Добавить **«Аудит»**,
   «Пользователи и роли», «Документооборот», «Нумерацию» — с фикстурами, где в записи аудита есть
   незамапленное действие, `entityType: "resolution"` и `newValue` с полями.
2. **Нет правил на технические ключи и имена полей.** В `FORBIDDEN` (строка 150) добавить:
   - ключ через точку: `/\b[a-z]+\.[a-z_]{2,}\b/`;
   - snake_case: `/\b[a-z]+_[a-z_]+\b/`;
   - имена полей: `docNumber|regNumber|entityType|sortOrder|isActive|dueSoonDays|fullName|oldValue|newValue|problemCode`;
   - фигурные скобки сериализации: `/\{\s*"/`.

## 8. Найдено сверх задачи

1. **Guard-тест не покрывает «Аудит» и «Пользователи и роли»** — поэтому F1–F4 в живом UI никто не
   поймал: тест проверяет `SettingsModal`, но открывает только четыре вкладки.
2. **Два независимых `ACTION_TITLES`** (`AuditTab.tsx:16` — 15 записей, `DocumentCard.tsx:40` — 6)
   с разными текстами. Один и тот же поступок называется по-разному в двух экранах.
3. **В `AuditTab` уже есть русские подписи объектов** (`ENTITY_OPTIONS`, строка 39), но колонка
   «Объект» их не применяет — карта есть, применение забыли.
4. **В `DocumentCard` уже импортирован `DOCUMENT_STATUS_TITLES`** (строка 17), но «что изменилось»
   печатает сырой `status: «new» → «on_resolution»`.
5. **В карте `ACTION_TITLES` есть ключи, которых не существует в коде** (`auth.login`,
   `auth.logout`, `settings.save`), и при этом нет реальных `login`, `login_failed`,
   `login_blocked`, `user.create`, `user.update` — карта расходится с сервером в обе стороны.
6. **`needed: 300` в API подсказки исполнителей** — это внутренний порог, попавший в текст для
   человека. Если он для чего-то нужен продукту, его надо назвать явно как продуктовый критерий;
   сейчас он выглядит как обещание.
