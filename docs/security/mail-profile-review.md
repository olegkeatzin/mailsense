Повод: в T35 `requireRemoteSession` начал запоминать пользователя подтверждённой сессии
(`req.user`), чтобы личным маршрутам в клиентском режиме было кого атрибутировать.

Артефакт теста: `packages/server/src/mailProfile.security.test.ts` (новый, 15 тестов).

## 1. Кэш пользователя НЕ обходит проверку сессии — вердикт OK

| Сценарий | Ожидание | Факт (код ответа) |
|---|---|---|
| Без cookie, GET и PUT `/api/mail-profile` | 401, профиль не читается и не пишется | **401 / 401**, `getMailProfile`/`setMailProfile` не вызваны |
| Подделанный (неизвестный серверу) токен | 401 | **401**, и к серверу ушёл ровно **1** запрос `/api/auth/me` |
| Подделанный токен на PUT | 401, без записи | **401**, `setMailProfile` не вызван |
| Сервер ответил 500 | 503 (не «вошёл», не «нет прав») | **503** |
| Токен не подтверждали, сервер недоступен | 503 — «уронить» сервер недостаточно, чтобы войти | **503** |
| Сессия отозвана (после разлогина), TTL истёк | 401, запись кэша сбрасывается | **401** |

## 2. Профиль только свой — вердикт OK

| Проверка | Факт |
|---|---|
| Ключ профиля = LDAP-логин владельца токена | `getMailProfile("ivanov_ii")` для токена A, `getMailProfile("petrova_ma")` для токена B |
| Нет LDAP-учётки (локальный админ) → ключ = id | `getMailProfile("u-c")` |
| Чужой ключ в query (`?userId=petrova_ma`) при токене A | ключ всё равно `ivanov_ii` |
| Чужой `userId` в теле PUT при токене A | `setMailProfile("ivanov_ii", {…signatureText})` — запись под своим ключом |

Механизм: `profileKey(req)` берёт `req.user.ldapUid || req.user.id` (`mailProfileRoutes.ts:37-41`);
никакого пользователя из запроса маршрут не принимает — IDOR-пути нет. Нет `req.user` →
`requireUser` бросает 401.

## 3. Офлайн-путь не расширяет права — вердикт OK

| Сценарий (сервер недоступен) | Факт |
|---|---|
| В пределах TTL | **200**, и к серверу обращений **не было вовсе** (кэш); профиль — владельца кэша |
| TTL истёк, сессия подтверждалась | **200**, профиль только владельца |
| TTL истёк, токен никогда не подтверждался (незнакомый) | **503** |
| Сервер вернулся и сказал «сессии нет» | **401** — кэш больше не спасает |

То есть офлайн-режим не выдаёт доступ никому, кроме того, чья сессия была подтверждена раньше, и
не открывает чужие данные: ключ всегда берётся из подтверждённого пользователя этого токена.

## 4. Приватность: подпись и имя физически не уезжают на сервер СЭД — вердикт OK

Живой прогон на стенде (учётка `user2@stand.test`, ключ профиля `user2`), с восстановлением
профиля первым действием в `finally`:

```
GET  /api/mail-profile            -> 200  (исходная подпись — пустая)
PUT  /api/mail-profile  {"signatureText":"ZZPROBE-SIGN-37"} -> 200
GET  /api/mail-profile            -> 200  маркер на месте: true
лог сервера  packages/server/data/logs/mailsense.log : совпадений маркера = 0

локальная SQLite packages/server/data/mailsense.sqlite, mail_profile(user_id='user2') :
    строка есть, маркер в signature_text = true (длина 15 = длина маркера)
ОТКАТ: PUT -> 200, профиль совпадает с исходным по всем полям: true,
       SQLite после отката совпадает с исходным: true
аудит сервера: строк было 2320, стало 2320 (правка профиля в аудит СЭД не попадает вовсе)
```

Почему так по построению:
- `/api/mail-profile` не входит ни в `DOCFLOW_PREFIXES`, ни в `MAIL_PREFIXES` (`proxy.ts:22-60`),
  поэтому `isProxiedPath("/api/mail-profile") === false` — в клиентском режиме запрос **не
  проксируется** (тест проверяет и подпути; для сравнения `/api/auth/me` и `/api/emails` — true).
- Ядро профиля (`core/src/services/mailProfileService.ts`) работает только с локальными
  `repos`: ни сети, ни docflow.
- Тест с маркером в подписи проверяет, что за время PUT ушёл **только** запрос проверки сессии
  `/api/auth/me` и ни один запрос не адресован профилю.

## 6. Находки

**R-1. Остаточный риск с границей: окно до 5 с после разлогина.** Локальный кэш
`remoteVerified` живёт `REMOTE_CHECK_TTL_MS = 5000`, а `/api/auth/*` в клиентском режиме
проксируется (`DOCFLOW_PREFIXES` начинается с `/api/auth`), поэтому локальный процесс **не видит
разлогин** и не сбрасывает запись: в течение ≤ 5 с старая cookie ещё даёт 200 на
`/api/mail-profile` с кэшированным пользователем.
Границы (доказаны тестами): окно **не больше TTL** (на TTL+1 мс — уже 401), и через него видно
**только свои** локальные данные — чужой профиль не открывается, а вторая сессия в том же окне
работает со своим ключом. Тот же украденный токен и без окна даёт доступ к локальной почте
(это свойство клиентского режима, а не этой правки).
Предложение (владельцу, не срочно): тримминг хранимого пользователя до `{id, ldapUid, fullName}`
вместо полного объекта с правами — уменьшает и объём, и ценность кэша; плюс, если когда-нибудь
локальный logout появится, сбрасывать запись по токену. **Дефектом не считаю**: ни (а) окно
больше TTL, ни (б) доступ к чужим данным не подтверждены — наоборот, оба проверены и опровергнуты.

**Наблюдение N-1.** `getMailProfile` в ядре валидирует ключ (`readUserId`) и бросает
`MailProfileInputError`; маршрут переводит это в 400. Но при пустом ключе маршрут до ядра не
доходит (срабатывает 401 от `requireUser`) — поведение верное, просто две защиты на один случай.

## 7. Что НЕ проверено и почему

- **Живой клиентский режим** (два процесса: клиент + сервер СЭД): стенд на 8123 работает локальным
  СЭД (в логе видны свои LDAP-бинды и IMAP, стартовой строки прокси нет), поэтому офлайн-путь и
  непроксируемость проверены детерминированно тестами, а не живым клиентом. По решению Lead'а
  второй экземпляр не поднимался.
- **Браузер** (личный профиль в интерфейсе, пустая консоль): зона qa-tester.
- **Логи самого процесса-клиента**: в клиентском режиме лог будет свой; у маркера проверен лог
  стенда. Если Lead поднимет живой клиент, повторю поиск там же.
