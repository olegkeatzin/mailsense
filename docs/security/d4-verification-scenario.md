## 9.1 Матрица (сырые коды)

```
СВОЁ поручение (Петрова — исполнитель)   admin 403  secretary 200  signer 403  manager 200  executor 200 | anon 401
ЧУЖОЕ поручение (Петрова не участник)    admin 200  secretary 403  signer 403  manager 403  executor 403 | anon 401
Поручение БЕЗ связанного письма          admin 403  secretary 404  signer 403  manager 403  executor 403 | anon 401
Несуществующее поручение                 404 всем                                                            | anon 401
```
Так и задумано: 200 — только участнику (исполнитель, подписант/утвердивший, автор, отправивший,
подтвердивший); 403 — существующее чужое; 404 — нет связи с письмом или поручения нет.
Админ НЕ получает доступ автоматически (он проходит только там, где он участник) — это правильно:
маршрут про поручение, а не про роль.

## 9.2 Вложения и подстановка (сильнейшие кейсы)

```
своё поручение + ЧУЖОЕ (реально существующее) вложение -> 404
своё поручение + мусорный id                            -> 404
своё поручение + 00000000-…                             -> 404
чужое поручение + его собственное вложение              -> 403
вложение без сессии                                     -> 401
положительный случай: участник (prepared_by) скачал вложение -> 200, байт 1 055 176
     = size в локальной SQLite = размер файла на диске (совпало побайтово)
```
Проверка связи стоит ДО выдачи файла, поэтому подстановка чужого `attachmentId` не работает: id
ищется среди вложений ТОГО письма, которое привязано к поручению.
