# Почта: приём, отправка, переписки

Путь данных: коннектор (IMAP/POP3) → `mailparser` → SQLite + файлы вложений на диске → очередь
`p-queue` → ИИ-адаптер (OpenAI-совместимый) → валидация JSON (zod) → `analysis_results`.
Статусы анализа: `pending` → `queued` → `processing` → `ready` | `error`.

## ⚠️ Message-ID уникален В ПРЕДЕЛАХ ЯЩИКА, а не глобально

Самая дорогая находка проекта: **письма, отправленные системой, не появлялись в ящике получателя.**
Почтовый сервер их доставлял, в «Отправленных» отправителя они лежали — а у адресата в приложении
их не было. Молча: ни ошибки, ни предупреждения.

Причина — два независимых дефекта, и оба били в одно место:

1. **`emails_message_id_idx` был UNIQUE по `message_id` без ящика.** `sendEmail` кладёт копию
   в «Отправленные» отправителя с тем же Message-ID — и когда скан доходил до ящика получателя,
   `emailExistsByMessageId` считал письмо уже известным и **отбрасывал его как дубликат**.
   Теперь уникальность — по паре `(account_id, message_id)` (миграция 12), а функция принимает
   `accountId` и без него не должна вызываться при сканировании.
2. **Номер миграции 11 был занят** исторической `edms_users_roles_sessions_audit` (следы первой
   реализации СЭД в SQLite). Новая миграция с тем же номером **молча пропускалась** как уже
   применённая — индекс оставался старым, а в журнале миграций всё выглядело благополучно.

⚠️ **Не занимайте чужие номера миграций.** Сверяйтесь с `schema_migrations` в живой базе, а не
только с исходником: в базе могут быть миграции, которых в коде уже нет.

```sql
SELECT version, name FROM schema_migrations ORDER BY version;
```

⚠️ **Одинаковый Message-ID у писем в разных ящиках — это норма, а не дубликат.** Одно письмо
законно лежит и в «Отправленных» отправителя, и в INBOX получателя. Дедупликация по Message-ID
допустима только внутри одного ящика.

Проверяется тестом: `repos.tombstones.test.ts` → «одно письмо в разных ящиках». Он ловит и
глобальную уникальность, и вызов `emailExistsByMessageId` без ящика.

## Диапазон дат в IMAP

Не передавай в `imapflow.fetch()` объект `{since, before}`: библиотека компилирует `BEFORE`/`SINCE`
в расширение `WITHIN` (`OLDER`/`YOUNGER`), которое Dovecot отвергает
(`BAD Invalid search interval parameter`) — и скан молча возвращает 0 писем.

В `imapConnector.ts` сначала получается СПИСОК UID (`SEARCH SENTSINCE/SENTBEFORE` при диапазоне,
иначе `SEARCH ALL`), из него вычитаются `knownUids`, и только после этого качаются тела
(`fetch(uidList, {source:true, uid:true}, {uid:true})`, пачками по 500).

Нельзя снова скачивать весь ящик через `fetch("1:*")` и фильтровать уже полученные письма —
на большом ящике скан без периода выглядит «зависшим». Фолбэк на `1:*` — только если SEARCH упал.
Плюс `mailService` фильтрует по `Date` на клиенте (в локальной зоне) — как страховка и для POP3.

**POP3** серверного поиска по датам не имеет: скачиваются все неизвестные UID, диапазон применяется
клиентски. ⚠️ POP3-клиент читает `latin1` (протокол байтовый): поддельный сервер в тестах обязан
писать байты, а не UTF-8, иначе кириллица в сравнениях превращается в мусор.

## Удаление и повторный скан

Удалённые письма пишутся в `deleted_emails` (надгробия): авто-скан (`includeDeleted=false`)
не воскрешает их, а ручной скан (`POST /api/accounts/:id/fetch`) передаёт `includeDeleted=true` —
тогда UID/Message-ID надгробий не считаются известными и письма скачиваются заново
(`clearDeletedEmail` снимает надгробие). Иначе «удалил → скан» навсегда ничего не возвращает.

## Авто-скан НЕ сканирует весь ящик

Планировщик берёт `account.settings.lastFetchAt` и забирает письма начиная с него (минус сутки
запаса). Пока синхронизации не было, авто-скан молчит — первичный скан запускает пользователь
кнопкой «Скан» (при необходимости с диапазоном дат). Отключение — настройка `auto_fetch=false`
(«Настройки → Общие»).

Параллельные сканы одного аккаунта сериализуются в `mailService` (иначе «Connection not available»
или socket timeout).

## Точка «письма добавлены» — `mailSyncHook`

После скана core отдаёт список добавленных писем через `setMailSyncHook`. Этим пользуется серверная
часть, чтобы распознать ответ руководителя (см. `docflow.md`). **Ошибка обработчика не роняет скан**
(`runMailSyncHook` ловит и логирует): письма уже сохранены, и терять из-за сбоя разбора весь скан
недопустимо.

## Переписки (threadService)

Приоритет — `In-Reply-To`/`References`; если родителя нет в БД, ответы склеиваются по нормализованной
теме (`Re:`/`Fwd:`/`Ответ:` срезаются, в т.ч. внутри строки); письма без признаков ответа с одинаковой
темой НЕ склеиваются (рассылки). Родитель, пришедший позже детей, «усыновляет» их.

При апгрейде беседы один раз пересобираются целиком — гейт `settings.maintenance.version`
(см. `services/maintenance.ts`). Ручная пересборка: `POST /api/threads/rebuild` (тело `{accountId?}`).

**Статус «Готово»** ставится только после успешного анализа. Ответы внутри переписки больше НЕ
помечаются готовыми без анализа: при `auto_analyze=false` они остаются «Ожидает».

## Вложения: текст и описание

OCR/извлечённый текст сохраняется в `attachments.extracted_text` (`setAttachmentText` из
`analysisService`), описания модели — в `ai_description`. Сопоставление описаний с вложениями идёт
через `matchAttachmentDescriptions` (регистр/путь/пробелы/расширение), а не строгим сравнением
`filename` — иначе часть вложений остаётся без «краткого содержания».

Обработка: изображения → OCR-модель (base64); PDF → рендер страниц в PNG (pdfjs-dist + @napi-rs/canvas)
→ OCR постранично; DOCX → текст (mammoth) + вложенные картинки; XLSX → структурированный текст (xlsx).
Staged-пайплайн: сначала OCR-модель (`glm-ocr`) параллельно, затем summary-модель text-only.
Параллельность — в «Настройки → ИИ» (`concurrency` / `ocrConcurrency`).

## Письма: ответ, пересылка, подпись

⚠️ **Вложения при пересылке не гоняются через JSON.** Шаблон `GET /api/compose-template` отдаёт
ссылки `{filename, mimeType, size, attachmentId, emailId}`, а клиент тянет файл по требованию
(`GET /api/emails/:id/attachments/:attId/file`) и кодирует в base64 только в момент отправки или
сохранения черновика. Раньше данные вложения целиком лежали в JSON: письмо на 20 МБ превращалось в
27 МБ ответа. Если вложение не удалось достать — письмо НЕ уходит, а сервер отвечает 400: тихая
отправка без файла запрещена.

⚠️ **Копия в «Отправленных» хранит вложения** (`sendService`): файл ложится на диск, в БД пишется
строка вложения без OCR. До 2026-10-06 записей не было вовсе — файлы уходили, а открыть их из
«Отправленных» было нельзя. Письма, отправленные раньше, остаются без вложений: миграции нет.

Шаблон для композера собирает `GET /api/compose-template` (`services/composeService.ts`): получатели
(Reply-To → From), тема без дублей `Re:`/`Fwd:`, цепочка `References` = references оригинала +
Message-ID родителя (`buildReferences`), строка атрибуции, цитата (`>` в text/plain, `<blockquote>`
в HTML) и подпись.

Подпись и отображаемое имя — в `account.settings` (`displayName`, `signature`, `signatureHtml`,
`signatureEnabled`, `signaturePosition`, `signatureDelimiter`, `replyQuote`, `replyAttribution`,
`forwardAttachments`) и правятся в «Настройки → Аккаунты → Отправка и подпись». Пересылка
прикладывает вложения оригинала. `signatureHtml` — подпись из WYSIWYG-редактора (приоритет),
`signature` — plain-зеркало для text/plain.

⚠️ Редактор TipTap отдаёт HTML; text/plain собирается `htmlToPlainText` (blockquote → `>`),
а не `editor.getText()` — иначе цитата теряет `>`.

⚠️ Адреса в «Кому/Копия» разбирает `parseEmails` (Composer.tsx) НЕ через split: имя вида
«Иванов, И.И. <a@b>» не должно рваться по запятой, поэтому ищутся готовые адреса
(`"Имя" <a@b>` / `Имя <a@b>` / `a@b`), а разделители просто игнорируются. В `AddressSelect`
`tokenSeparators={[";"]}` — запятая намеренно НЕ разделитель (иначе имя рвётся при вводе).

## Единый WYSIWYG-редактор

`components/RichTextEditor.tsx` (TipTap StarterKit + Placeholder) — один редактор на композер,
шаблоны и подпись: панель с заголовками, списками, цитатой, ссылкой и «Tx».
**Не плодить второй экземпляр TipTap** — переиспользовать этот компонент.

## Шаблоны писем

«Настройки → Шаблоны»: список + кнопка «Добавить шаблон», форма — в **попапе** (встроенной формы
под списком больше нет). Сохраняются `bodyHtml` (WYSIWYG) и `bodyText` (plain-фолбэк).

⚠️ Модалка настроек НЕ размонтирует вкладки, поэтому в `SettingsModal` они пересоздаются по
`reloadKey` при каждом открытии — иначе список шаблонов (и статус каталога) остаются устаревшими,
и сохранённый из композера шаблон «не появляется» в настройках.

## Каталог LDAP/AD (адресная книга)

Вход опционален (`services/directoryService.ts`, `directory/ldap.ts`, `ldapts`): bind от учётки
пользователя, пароль зашифрованно (`settings`: `ldap.login`/`ldap.passwordEncrypted`). Настройки —
`ldap.*` (`url`, `baseDn`, `loginFormat`, `upnSuffix`, `netbiosDomain`, `userFilter`, `attributes`,
`sizeLimit`, `rejectUnauthorized`), UI — «Настройки → Каталог (LDAP)». Автокомплит адресов —
`GET /api/contacts/search` (кэш таблицы `contacts` + онлайн-дополнение).

⚠️ `upnSuffix` может содержать ведущий `@` — не удваивать (`buildBindIdentifier`).
⚠️ **Только LDAPS**: на стенде `ldap://…:389` рвёт соединение на TLS, нужен `ldaps://127.0.0.1:636`
с `rejectUnauthorized: false`. И не искать от корня домена — AD отвечает referrals.
⚠️ `ldapts` объявлен в `dependencies` и у `@mailsense/core`, и у `apps/electron` (external для tsup) —
иначе electron-builder не положит его в asar.

⚠️ **Не ищите в SQLite через `lower()`.** SQLite понимает только ASCII: запрос «иван» не находил
«Иванов Иванов», то есть русские имена в автодополнении не искались. `searchContactsCache` сравнивает
строки в JS — не возвращайте сюда `lower()`. **В PostgreSQL та же задача решается через `ILIKE`** —
там свёртка регистра кириллицы работает (проверено: `lower('ИВАНОВ')` → `иванов`).

## Прочие подводные камни

- Seeding тестового аккаунта выключен по умолчанию. Для локального стенда задай env:
  `MAILSENSE_SEED_ACCOUNT=true MAILSENSE_MAIL_USER=test@mail.test MAILSENSE_MAIL_PASS=<пароль>`
  (или добавь аккаунт через окно настроек).
- Пароли: в Electron — `safeStorage`, иначе фолбэк AES-256-GCM (ключ в `data/secret.key`).
- POP3: после `RETR`/`UIDL` сначала идёт строка статуса `+OK …` — её нужно читать отдельно от тела
  (см. `pop3Client.ts`).
- Изменения в палитре настроек аккаунта (`settings`) читаются как строки: `"false"` — это правда
  строка, а не boolean.
