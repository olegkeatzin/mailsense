# ТЗ: Интеграция модуля СЭД в почтовый клиент

**Цель:** Расширить функционал почтового клиента до легковесной системы электронного документооборота (СЭД) для ведения электронного журнала регистрации входящих документов (на основе бумажного аналога) и автоматизации процесса наложения резолюций.

## 1. Архитектура и стек
*   **Клиент-серверная архитектура:** Клиент (Desktop/Web) ↔ API-сервер (Backend) ↔ БД (PostgreSQL) ↔ LDAP/AD.
*   **API:** REST или GraphQL для взаимодействия клиента с бизнес-логикой СЭД.
*   **Кэширование:** Redis для сессий и очередей уведомлений.

## 2. Авторизация и управление доступом (LDAP/AD)
*   **Аутентификация:** Вход в клиент через LDAP (bind-запрос). Пароли не хранятся в БД приложения.
*   **Синхронизация профилей:** ФИО, email, отдел, должность, руководитель подтягиваются из LDAP (LDAP — источник истины).
*   **Роли (RBAC):** Роли хранятся в локальной БД (LDAP — источник истины только для кадровых данных).
    *   `Секретарь/Аппарат`: доступ к журналу, регистрация, архивация.
    *   `Руководитель`: наложение резолюций, контроль.
    *   `Исполнитель`: получение задач, отчет об исполнении.
    *   `Администратор`: доступ к админ-панели.
*   **Увольнение:** При отсутствии пользователя в LDAP — блокировка входа, но сохранение истории в БД (`is_active = false`).

## 3. Модель данных (Схема БД)
Необходимо создать следующие сущности:
*   **`Users`**: `id`, `ldap_uid`, `email`, `full_name`, `department`, `role_id`, `is_active`.
*   **`Documents` (Записи журнала)**:
    *   `incoming_number` (генерируется автоматически)
    *   `incoming_date` (автоматически)
    *   `doc_number_and_date` (вручную, из письма)
    *   `sender` (автоматически из поля From)
    *   `summary` (автозаполнение из Subject, редактируемое)
    *   `sheets_count` (вручную или подсчет страниц PDF)
    *   `resolution_text` (текст резолюции)
    *   `assignee_id` (FK на Users)
    *   `deadline` (срок исполнения)
    *   `status` (Enum: Новый, На резолюции, На исполнении, Исполнен, В архиве)
    *   `execution_date` (фактическая дата)
    *   `case_number` (№ дела)
    *   `document_name` (финальное наименование)
*   **`Audit_Log`**: `id`, `user_id`, `action`, `entity_id`, `timestamp`, `old_value`, `new_value`.

## 4. Бизнес-процессы (Workflow)

### Сценарий А: Регистрация входящего
1.  Письмо попадает в Inbox.
2.  Секретарь нажимает «Зарегистрировать». Система проверяет дубли.
3.  Открывается форма с автозаполненными полями. Секретарь дополняет и сохраняет.
4.  Системе присваивает `incoming_number` по заданному формату.

### Сценарий Б: Наложение резолюции (Ключевой процесс)
1.  Руководитель открывает письмо и нажимает «Наложить резолюцию».
2.  Заполняет: текст, исполнителя (из LDAP), срок.
3.  Система формирует структурированное письмо и отправляет его **Аппарату** и **Исполнителю**.
4.  **Аппарат:** Система автоматически создает черновик записи в Журнале. Аппарат проверяет данные, вписывает № листов и нажимает «Зарегистрировать». Запись фиксируется, блокируется от изменений.
5.  **Исполнитель:** Получает уведомление (email). В карточке задачи видит резолюцию, срок и ссылку на исходный документ.

### Сценарий В: Исполнение и архивация
1.  Исполнитель нажимает «Отчитаться об исполнении», прикрепляет файлы.
2.  Создается связанное исходящее письмо.
3.  Аппарат получает уведомление, проверяет, вписывает `case_number` и переводит статус в «В архиве».

## 5. Требования к UI/UX
*   **Панель чтения (Reading Pane):** Боковая панель «СЭД» в открытом письме с кнопками «Зарегистрировать» и «Наложить резолюцию».
*   **Раздел «Журнал»:** Отдельный пункт меню. Таблица (DataGrid) с фильтрацией, сортировкой и поиском, визуально повторяющая бумажный журнал.
*   **Kanban-доска для руководителя:** Колонки: «Новые», «На резолюции», «В работе», «Просрочено», «Выполнено». Drag-and-drop карточек.
*   **Входящие на регистрацию (для Аппарата):** Список карточек, требующих действия, а не обычная почта.
*   **Связывание (Threading):** Все письма по одному документу (входящее, резолюция, отчет) должны быть сгруппированы в одну цепочку (через `In-Reply-To`/`References` или связи в БД) - уже есть реализация в почте

## 6. Админ-панель (Обязательный функционал)
*   **Управление пользователями:** Просмотр синхронизированных сотрудников, назначение ролей, ручное создание внешних контрагентов.
*   **Настройки нумерации:** Префиксы, форматы (`{Префикс}-{Год}-{Номер}`), правила сброса счетчика, разделение по потокам.
*   **Справочники:** Номенклатура дел, шаблоны резолюций, типовые сроки исполнения.
*   **Аудит:** Просмотр логов действий, экспорт журнала в Excel/CSV.
*   **Настройки шлюза:** Правила автосортировки писем (например, с ящика `info@` автоматически создавать документ).

## 7. Технические вызовы и требования
*   **Транзакционность:** Генерация входящего номера должна быть атомарной (защита от дублей при одновременной регистрации).
*   **Уведомления:** email-напоминания о дедлайнах.
*   **Поиск:** Полнотекстовый поиск по телу письма, резолюциям и краткому содержанию - реализовано в почте
*   **Безопасность:** Разграничение прав на редактирование (Руководитель не может редактировать журнал, Аппарат не может менять текст резолюции).
